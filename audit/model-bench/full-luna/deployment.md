### 1.1 회의에서 확인된 배포 관련 결정

- iOS와 안드로이드 앱을 함께 출시합니다.
- React Native를 이용한 크로스플랫폼 개발 방향이 논의됐습니다.
- 앱 빌드 및 배포 파이프라인은 초기에 마련해야 합니다.
- 7주 차 초반 베타 빌드, 7주 차 말 스토어 제출을 목표로 합니다.
- 8주 차는 출시 후보 및 심사 제출 목표 주간입니다. 실제 공개일은 베타 결과와 스토어 심사 통과 후 정합니다.
- 스토어 심사 지연에 대비해 9주 차를 완충 기간으로 둡니다.
- 서버는 국내 리전 사용이 가능하다고 논의됐지만, 클라우드 사업자와 실제 배포 구성이 정해진 것은 아닙니다.
- 자동 백업, 백업 암호화, 접근 권한 관리와 출시 전 복구 시험이 필요합니다.
- 서버 오류율, 응답 시간, 저장 실패율을 살펴보고, 외부 API와 서버 비용은 사용량 알림 및 호출 제한으로 관리하는 방향입니다.
- 오류·진단 자료에는 앱 버전, 플랫폼, 오류 코드, 요청 ID 등 필요한 정보만 남기고, 음식명·칼로리·체중·자유 입력 내용은 포함하지 않습니다.
- 외부 식품 데이터 공급자, 인증 제공자, 푸시 업체, 분석 도구, 실제 서버·스토어 배포 계정과 권한은 미확정입니다.

## 2. 배포 환경

회의에서 실제 환경 주소, 데이터베이스 제품, 서버 사양과 배포 플랫폼은 확정되지 않았습니다. 아래 표는 환경 분리와 출시 절차를 위한 **구성 제안**입니다. 실제 주소와 리소스는 개발팀과 운영 담당자가 확정해야 합니다.

| 환경 | 주소 | 용도 | 데이터베이스 | 리소스 |
|---|---|---|---|---|
| 개발자 로컬 | 미정. 예: `http://localhost:<서버_포트>` | 기능 개발, 단위 시험, 개인별 검증 | 미정. 실제 데이터와 분리된 로컬용 저장소 권장 | 개발자 장비 기준. 서버 사양 해당 없음 |
| 개발 서버 | 미정. 예: `https://api-dev.<도메인>` | 앱·서버 통합 개발, 임시 시험 자료 검증 | 개발용 분리 데이터베이스 제안 | **추정 필요** |
| 스테이징 서버 | 미정. 예: `https://api-staging.<도메인>` | 출시 후보와 유사한 조건의 승인·베타 시험 | 운영 자료와 분리된 스테이징 데이터베이스 제안 | **추정 필요** |
| 프로덕션 서버 | 미정. 예: `https://api.<도메인>` | 사용자 대상 서비스 운영 | 운영 전용 데이터베이스 제안 | **추정 필요** |
| iOS 시험 배포 | App Store Connect 및 TestFlight 사용 여부 미정 | 사내·외부 베타 배포 | 앱이 연결하는 개발·스테이징 API 환경에 따라 구분 | 모바일 기기 기준 |
| 안드로이드 시험 배포 | Google Play Console 내부·비공개 시험 경로 사용 여부 미정 | 사내·외부 베타 배포 | 앱이 연결하는 개발·스테이징 API 환경에 따라 구분 | 모바일 기기 기준 |
| iOS 공개 배포 | App Store | 승인된 출시 빌드 공개 | 프로덕션 API | 모바일 기기 기준 |
| 안드로이드 공개 배포 | Google Play | 승인된 출시 빌드 공개 | 프로덕션 API | 모바일 기기 기준 |

> 위 주소 예시는 형식 설명용입니다. 실제 도메인, 서버 사양, 저장소 제품, 시험 배포 방식이 정해졌다는 뜻이 아닙니다.

### 2.1 환경 분리 원칙

- 개발·스테이징·프로덕션의 데이터베이스와 비밀 정보를 서로 분리합니다.
- 프로덕션 식사 기록을 개발·스테이징 시험에 복사하지 않습니다.
- 시험 사용자를 위한 자료는 가상 식단 또는 별도 시험 계정으로 관리합니다. 베타에서 실제 기록을 다루는 경우에는 별도 동의, 사용 목적, 보관 기간 및 삭제 방법을 안내해야 합니다.
- 앱 빌드가 어떤 API 환경에 연결되는지 빌드 시점에 명확히 정하고, 스토어 공개 빌드가 개발 서버를 바라보지 않는지 출시 전에 확인합니다.
- 음식 검색 API의 검색어 전달 조건과 계약을 확인하기 전에는 운영 환경에서 공급자 연동을 활성화하지 않습니다.
- 분석 수집에 동의하지 않아도 앱 기능을 사용할 수 있어야 합니다. 제품 분석과 보안·장애 대응 로그는 분리합니다.
- 프로덕션 데이터와 비밀 정보에 대한 접근 권한은 필요한 역할로 제한합니다. 구체적인 역할·승인 체계는 운영 정책 확정이 필요합니다.

### 2.2 접근 방식

서버 접속 방식과 접근 주소는 확정되지 않았습니다. 아래는 인증된 운영 계정과 비밀키를 사용하는 경우의 **명령 예시**입니다. 주소·계정·인증 방식은 실제 운영 구성을 확인한 뒤 치환해야 합니다.

```bash
# 개발 서버 예시: 실제 접속 주소와 계정은 추정 필요
ssh <개발_계정>@<개발_서버_주소>

# 스테이징 서버 예시: 실제 접속 주소와 계정은 추정 필요
ssh <스테이징_계정>@<스테이징_서버_주소>

# 프로덕션 서버 예시: 접근 승인 후 사용
ssh <운영_계정>@<운영_서버_주소>
```

프로덕션 접속 자격 증명을 저장소에 올리거나 개인 메신저로 전달하지 않습니다. 서버 직접 접속이 필요한지, 운영 제어창이나 배포 자동화를 통해서만 배포할지는 인프라 확정 단계에서 결정해야 합니다.

## 3. 사전 요구사항

| 항목 | 최소 기준 | 권장 기준 | 상태 |
|---|---|---|---|
| 운영체제 | macOS 또는 지원되는 개발 운영체제 | iOS 빌드 담당자는 Xcode를 실행할 수 있는 macOS 환경 | 제안. 팀 환경 확인 필요 |
| Node.js | 프로젝트가 정한 버전 | 프로젝트 버전 고정 파일에 지정된 버전 | 버전 추정 필요 |
| 패키지 관리자 | 저장소에서 정한 도구 | 잠금 파일과 일치하는 버전 | 도구 미정 |
| React Native | 프로젝트에 고정된 버전 | 개발·시험·출시 빌드에서 동일한 의존성 사용 | 회의에서 개발 방향 논의, 버전 미정 |
| Xcode | 앱 저장소와 호환되는 버전 | 개발자와 배포 자동화에서 동일한 버전 | 버전 추정 필요 |

**설치 확인 명령 예시**

```bash
node --version
npm --version
git --version
```

React Native 프로젝트의 설치·실행 명령은 앱 저장소의 실제 구성에 따라 달라집니다. 다음 명령은 `npm`을 사용하는 경우의 **예시**이며, 저장소에 `yarn.lock` 또는 다른 잠금 파일이 있다면 해당 도구를 사용해야 합니다.

```bash
# 저장소를 받은 뒤
git clone <앱_저장소_주소>
cd <앱_저장소_경로>

# 저장소의 버전 고정 파일을 확인
ls -la

# npm 잠금 파일이 있는 경우에만 사용
npm ci
```

> `npm ci`를 실행하기 전에 저장소에 `package-lock.json`이 있는지 확인합니다. 회의에서는 패키지 관리자나 의존성 설치 명령을 확정하지 않았습니다.

## 4. 환경 변수

회의에서는 실제 환경변수 이름이나 값이 정해지지 않았습니다. 아래 항목은 애플리케이션에서 필요할 수 있는 **구성 제안**입니다. 실제 이름과 저장 위치는 앱·서버 구현에 맞춰 확정합니다.

### 4.1 변수 관리 원칙

- 비밀값을 소스 코드, 앱 저장소, 배포 명령 기록 또는 공개 문서에 저장하지 않습니다.
- 프로덕션 비밀값은 개발·스테이징과 분리합니다.
- 앱에 포함되는 설정과 서버 비밀값을 구분합니다. 서버 비밀값을 모바일 앱에 넣으면 안 됩니다.
- 클라이언트에 포함되는 API 주소 등 공개 설정에도 비밀값이 들어가지 않도록 합니다.
- 인증 제공자 비밀키, 데이터베이스 접속 정보, 푸시 자격 증명, 외부 식품 API 키는 운영 접근 권한을 제한합니다.
- 환경변수 출력 명령으로 비밀값을 배포 기록이나 로그에 노출하지 않습니다.
- 제품 분석은 선택 동의를 거부해도 앱 기능이 정상 동작하도록 구성합니다.
- 음식명·칼로리·체중·자유 입력 내용은 제품 분석이나 일반 장애 로그에 전달하지 않도록 구현을 확인합니다.

### 4.2 서버에서 검토할 설정 항목

아래 표의 이름은 **설계 예시**이며 실제 구현 변수명이 아닙니다.

| 설정 항목 예시 | 적용 대상 | 용도 | 상태 |
|---|---|---|---|
| `APP_ENV` | 서버 | 개발·스테이징·프로덕션 구분 | 이름·허용값 추정 필요 |
| `PORT` | 서버 | API 서버가 수신할 포트 | 구현 확인 필요 |
| `DATABASE_URL` | 서버 | 데이터베이스 접속 | 데이터베이스 제품·주소·변수명 미정 |
| `AUTH_PROVIDER_*` | 서버 | 확정된 인증 제공자 설정 | 제공자 범위 미확정 |
| `FOOD_PROVIDER_*` | 서버 | 외부 음식 검색 공급자 설정 | 공급자·계약 미확정 |
| `PUSH_PROVIDER_*` | 서버 | 푸시 전달 자격 증명 | 공급자·구성 미정 |
| `PRODUCT_ANALYTICS_*` | 서버·앱 | 선택적 제품 분석 설정 | 도구 미정. 동의·국외 처리 검토 필요 |
| `ERROR_MONITORING_*` | 서버·앱 | 오류 코드 및 진단 자료 수집 설정 | 도구 미정. 민감 자료 차단 확인 필요 |
| `LOG_LEVEL` | 서버 | 운영 로그 상세 수준 | 값과 운영 정책 추정 필요 |
| `PUBLIC_API_BASE_URL` | 앱 빌드 | 앱이 연결할 API 주소 | 실제 주소 미정 |
| `APP_VERSION` | 앱 빌드 | 앱 버전 진단 | 저장소 버전 규칙 추정 필요 |

`FOOD_PROVIDER_*` 설정을 실제 운영에 넣기 전에는 공급자의 사용권, 검색어 처리, 비용, 호출 제한, 캐시 허용 조건을 확인해야 합니다. 확인되지 않은 공급자 정보를 프로덕션에 활성화하지 않습니다.

### 4.3 환경별 설정 예시

아래는 변수 이름을 설명하기 위한 예시입니다. 실제 값은 비밀 정보 저장소나 승인된 배포 설정에서 주입하며, 비밀번호·토큰·접속 주소를 문서에 기재하지 않습니다.

```dotenv
# 개발 환경 예시. 실제 변수명과 값은 추정 필요
APP_ENV=development
PUBLIC_API_BASE_URL=<개발_API_주소>
DATABASE_URL=<개발용_데이터베이스_접속값>
LOG_LEVEL=<개발용_로그_수준>
```

```dotenv
# 스테이징 환경 예시. 실제 변수명과 값은 추정 필요
APP_ENV=staging
PUBLIC_API_BASE_URL=<스테이징_API_주소>
DATABASE_URL=<스테이징용_데이터베이스_접속값>
LOG_LEVEL=<스테이징용_로그_수준>
```

```dotenv
# 프로덕션 환경 예시. 실제 변수명과 값은 추정 필요
APP_ENV=production
PUBLIC_API_BASE_URL=<프로덕션_API_주소>
DATABASE_URL=<운영용_데이터베이스_접속값>
LOG_LEVEL=<운영용_로그_수준>
```

### 4.4 설정 검증

구현된 설정 검증 명령이 있는 경우 해당 명령을 사용합니다. 실제 검증 스크립트는 미정이므로 아래는 **명령 작성 형태의 예시**입니다.

```bash
# 실제 저장소에 해당 검증 명령이 있는지 먼저 확인
cat package.json
```

```bash
# 다음 명령은 예시이며 실제 등록 여부를 확인해야 함
npm run config:check
```

검증 명령이 없다면 배포 전에 최소한 다음 사항을 수동으로 확인합니다.

- 현재 대상 환경과 앱 빌드의 API 주소가 일치하는가?
- 필수 인증·음식 검색·푸시 설정이 해당 환경에만 적용됐는가?
- 개발·스테이징 자료가 프로덕션에서 사용되지 않는가?
- 음식명·칼로리·체중·자유 입력 내용이 일반 로그나 분석 설정에 포함되지 않는가?
- 외부 업체의 처리 조건 및 동의 안내가 승인됐는가?
- 서명 자격 증명과 서버 비밀값이 저장소에 들어 있지 않은가?

## 5. 빌드 절차

회의에서 실제 빌드 스크립트, 패키지 관리자, 빌드 자동화 도구와 앱 버전 규칙은 정해지지 않았습니다. 아래 절차는 배포 시 검토할 **제안 흐름**입니다. 명령어는 저장소에서 실제로 제공하는 스크립트와 일치하는지 확인한 뒤 사용합니다.

### 5.1 공통 사전 확인

```bash
# 저장소 상태 확인
git status --short

# 현재 작업 위치와 저장소 구성 확인
pwd
ls -la

# 사용 중인 잠금 파일과 프로젝트 명령 확인
ls -1 package.json package-lock.json yarn.lock pnpm-lock.yaml 2>/dev/null
cat package.json
```

배포할 소스는 승인된 변경을 포함한 버전 관리 커밋이어야 합니다. 로컬에서만 수정된 파일이 없는지 확인합니다.

```bash
# 저장되지 않은 변경이 있는지 확인
git status --short

# 배포 대상 커밋 확인
git log -1 --oneline
```

### 5.2 앱 검증 및 빌드

React Native 앱의 실제 검사·시험 명령은 저장소 설정 확인 후 확정합니다. 다음은 스크립트가 등록되어 있는 경우의 예시입니다.

```bash
# 의존성 설치 예시: npm 잠금 파일 사용이 확인된 경우
npm ci

# 다음 명령은 저장소에 해당 스크립트가 있을 때만 실행
npm run lint
npm run test
npm run type-check
```

저장소에 스크립트가 없으면 임의로 명령을 만들어 실행하지 말고, 실제 `package.json` 및 빌드 문서에 등록된 검증 절차를 사용합니다.

빌드 전 점검:

- iOS와 안드로이드가 같은 승인된 앱 버전을 사용하는지 확인합니다.
- 개발·스테이징·프로덕션 API 주소가 의도한 빌드 대상과 일치하는지 확인합니다.
- 출시 빌드에 개발용 서버 주소, 시험용 계정, 임시 자격 증명이 포함되지 않았는지 확인합니다.
- iOS·안드로이드 서명 설정과 배포 권한을 확인합니다.
- 위치, 주소록 등 불필요한 권한을 요청하지 않는지 확인합니다.
- 알림은 사용자 선택형이며 기본값이 꺼져 있는지 확인합니다.
- 푸시 문구에 음식명·칼로리·체중 등 개인 기록이 포함되지 않는지 확인합니다.
- 제품 분석 이벤트에 음식명·칼로리·체중·자유 입력 내용이 포함되지 않는지 확인합니다.
- 사진 자동 인식과 사진 첨부는 최종 합의된 출시 범위에 맞게 포함 여부를 확인합니다. 회의 결정에서 사진 첨부 관련 상충 내용이 있으므로, 승인되지 않은 기능을 출시 빌드에 임의로 추가하지 않습니다.
- 검색 결과 없음과 API 오류가 구분되고, 직접 입력 경로가 동작하는지 확인합니다.
- 저장 실패 시 입력 내용이 보존되고 재시도 중 중복 기록이 생기지 않는지 확인합니다.

### 5.3 서버 이미지 또는 실행 산출물 만들기

서버 배포 방식은 회의에서 확정되지 않았습니다. 컨테이너를 사용하는 경우 다음은 **제안 예시**입니다. 실제 저장소에 `Dockerfile`과 빌드 절차가 마련된 경우에만 실행합니다.

```bash
# 저장소에 Dockerfile이 있는지 확인
test -f Dockerfile && echo "Dockerfile 확인" || echo "Dockerfile 없음"
```

```bash
# 실제 이미지 이름과 버전을 확정한 뒤 사용
docker build \
  --tag <이미지_저장소>/<서비스명>:<버전_또는_커밋_식별값> \
  .
```

배포 이미지에는 다음 자료가 포함되지 않도록 확인합니다.

- `.env` 파일과 비밀값
- 개발용·스테이징용·프로덕션용 데이터베이스 자료
- 실제 사용자 기록 또는 운영 데이터
- 개발자 개인 인증서와 서명 자격 증명
- 디버그 로그에 남은 사용자 입력값

### 5.4 배포 산출물 기록

배포 전에 다음 정보를 배포 기록에 남깁니다. 기록 위치와 담당자는 미정입니다.

| 항목 | 기록할 값 |
|---|---|
| 앱 버전 | 실제 출시 후보 버전 |
| 서버 버전 | 실제 배포 버전 또는 커밋 식별값 |
| 배포 환경 | 개발·스테이징·프로덕션 중 하나 |
| 소스 커밋 | 승인된 커밋 식별값 |
| 데이터베이스 변경 | 변경 파일·실행 순서·복구 방안 |
| 외부 연동 | 적용된 음식 검색·인증·푸시·분석 설정 |
| 승인 내역 | 개발·QA·운영·개인정보 검토 여부 |
| 배포 시각 | 실제 작업 시작·완료 시각 |
| 롤백 기준 | 장애 판단과 되돌림 조건 |

## 6. 배포 절차

배포 플랫폼, 서버 구성, 앱 배포 자동화 도구는 회의에서 확정되지 않았습니다. 이 절차는 플랫폼이 정해진 뒤 구현할 수 있도록 **환경별 승인 단계와 안전 통제**를 정의합니다. 아래 명령어는 실제 배포 도구가 확정된 것으로 오해하지 않도록 예시와 확정 필요 항목을 구분합니다.

### 6.1 개발 환경 배포

1. 개발 환경 API 주소, 데이터베이스, 인증·음식 검색 설정을 확인합니다.
2. 개발용 데이터베이스가 프로덕션과 분리돼 있는지 확인합니다.
3. 변경 내용을 개발 브랜치에 반영하고 검토를 받습니다.
4. 앱·서버 검증을 실행합니다.
5. 서버를 배포하고 데이터베이스 변경을 적용합니다.
6. 개발용 앱 빌드를 설치해 가입, 음식 검색, 직접 입력, 기록 저장·수정·삭제와 리포트 조회를 확인합니다.

```bash
# 1. 배포 대상 커밋 확인
git status --short
git log -1 --oneline

# 2. 저장소에 정의된 검증 명령 실행
# 아래 명령은 저장소에 실제 등록된 경우에만 실행
npm run lint
npm run test
```

서버 배포 명령은 배포 플랫폼 확정 후 작성합니다. 컨테이너 기반인 경우의 형식 예시는 다음과 같습니다.

```bash
# 예시: 실제 이미지 저장소·환경 파일·서비스 이름은 추정 필요
docker compose --env-file <개발_환경_설정_경로> pull
docker compose --env-file <개발_환경_설정_경로> up -d
docker compose ps
```

개발 환경 확인 후 문제를 발견하면 개발 환경에서 먼저 수정하고, 같은 변경을 스테이징으로 승격합니다. 환경마다 서로 다른 소스 수정본을 따로 운영하지 않습니다.

### 6.2 스테이징 배포 및 승인

스테이징은 출시 후보와 비슷한 설정으로 검증하되 실제 사용자 정보와 분리합니다.

1. 개발 환경의 시험을 통과한 동일한 소스 커밋을 선택합니다.
2. 스테이징 전용 자격 증명과 데이터베이스를 적용합니다.
3. 스테이징 데이터베이스 백업 또는 되돌리기 방법을 확인합니다.
4. 데이터베이스 변경을 적용합니다.
5. 앱 시험 빌드를 배포합니다.
6. iOS·안드로이드 기기별 검증과 API 통합 검증을 진행합니다.
7. 개인정보, 계정 삭제, 푸시 동의, 오류 로그, 외부 검색어 처리 조건을 확인합니다.
8. 주요 결함이 해결되고 출시 승인자가 확인한 뒤 프로덕션 배포를 요청합니다.

```bash
# 예시: 실제 배포 도구 및 옵션은 추정 필요
docker compose --env-file <스테이징_환경_설정_경로> pull
docker compose --env-file <스테이징_환경_설정_경로> up -d
docker compose ps
```

스테이징 승인 점검에는 다음 항목을 포함합니다.

- API 서버 기동 및 데이터베이스 연결
- 사용자별 음식·기록 데이터 분리
- 검색 결과 없음과 공급자 오류의 구분
- 직접 입력한 음식의 영양값 없음 처리
- 기록 시점 영양값 스냅샷 유지
- 한국 시간 기준 날짜 및 주간 리포트 집계
- 저장 실패·재시도 시 입력 보존 및 중복 방지
- 계정 삭제 요청과 연관 기록 삭제 흐름
- 분석 동의 철회 후 제품 분석 중단 여부
- 알림 기본 꺼짐, 사용자 설정 시간, 당일 기록이 있을 때 발송 생략
- 푸시 본문에 민감한 식단 정보가 없는지
- 로그에 음식명·칼로리·체중·자유 입력 내용이 없는지
- 백업 복구 시험 결과

### 6.3 iOS·안드로이드 베타 배포

베타 빌드와 스토어 시험 배포 도구의 실제 설정은 미정입니다. 회의에서는 7주 차 초반 베타 빌드를 목표로 했으며, 프로토타입 테스트와 베타 빌드 테스트를 구분했습니다.

#### 베타 배포 전

- 프로토타입 시험에는 가상 식단을 사용합니다.
- 실제 식단 기록을 다루는 베타 시험은 목적·수집 자료·보관 기간·삭제 방법을 안내하고 별도 동의를 받습니다.
- 시험 계정을 일반 서비스 분석에서 제외하거나 시험 계정임을 구분합니다.
- 시험 빌드가 프로덕션 API로 연결되지 않도록 주소와 자격 증명을 확인합니다.
- 외부 참가자의 연락처와 사례금 지급 자료가 필요한 경우 시험 자료와 분리해 처리합니다.
- 시험이 끝난 뒤 식사 기록 등 시험 자료를 삭제할 방법과 시점을 정합니다.
- 안드로이드 기기 2종 이상, iPhone 2종 이상을 포함한 기기 검증을 준비합니다. 실제 기기 보유 여부와 시험 범위는 확인이 필요합니다.

#### 시험 배포

스토어 시험 배포 명령은 회의에서 정하지 않았습니다. 배포 도구의 공식 절차를 확정한 뒤 적용합니다. 배포 기록에는 다음을 남깁니다.

- 베타 빌드 버전과 소스 커밋
- 사용한 API 환경
- 시험 참여자 범위 및 동의 상태
- 시험 기간과 자료 삭제 예정
- 시험 중 확인할 핵심 시나리오
- 주요 결함과 수정 빌드 번호

베타에서 볼 지표는 첫 식단 기록 완료율, 기록 완료 시간, 주간 기록 일수, 검색 실패 후 이탈, 직접 입력 비율, 리포트 조회율 등입니다. 사전에 수치 목표를 고정하기보다 기준선을 확보하고 인터뷰·관찰 결과와 함께 해석합니다. 주요 기록 흐름 완료율 95% 이상, 치명적인 데이터 유실 0건, 크래시 없는 세션 비율 99% 이상은 회의에서 제안된 베타 품질 목표이며 실제 승인 기준으로 확정하기 전에 표본과 결과를 확인해야 합니다.

### 6.4 프로덕션 배포

프로덕션 공개는 8주 안에 보장된 약속이 아닙니다. 8주 차는 후보 빌드 및 심사 제출 목표이고, 실제 공개일은 베타 결과와 스토어 심사 통과 후 정합니다. 9주 차는 심사 지연에 대비한 완충 기간입니다.

프로덕션 배포는 다음 순서를 따르는 **운영 제안**입니다.

1. 스테이징에서 승인된 소스 커밋과 앱 빌드 번호를 확정합니다.
2. 프로덕션 환경 변수와 접근 권한을 검토합니다.
3. 프로덕션 데이터베이스의 백업 상태와 복구 가능성을 확인합니다.
4. 데이터베이스 변경이 있는 경우 변경 계획과 복구 방안을 승인받습니다.
5. 서버 변경을 배포하고 헬스 상태를 확인합니다.
6. 프로덕션 API에 연결하는 iOS·안드로이드 출시 빌드를 제출합니다.
7. 스토어 심사 결과와 베타 결함 현황을 검토합니다.
8. 승인 이후에 공개 여부와 공개 시점을 결정합니다.
9. 공개 직후 저장 성공률, 오류율, 응답 시간, 앱 기동·충돌 현황, 비용을 감시합니다.

```bash
# 예시: 실제 도구·환경 파일·서비스 이름은 추정 필요
# 프로덕션 접근과 배포 승인 후에만 실행
docker compose --env-file <프로덕션_환경_설정_경로> pull
docker compose --env-file <프로덕션_환경_설정_경로> up -d
docker compose ps
```

위 예시 명령은 컨테이너 배포를 확정하는 내용이 아닙니다. 실제 배포 플랫폼이 결정되기 전까지 운영 서버에 그대로 복사해 실행해서는 안 됩니다.

### 6.5 배포 빈도·시간·중단 시간

| 항목 | 현재 상태 |
|---|---|
| 배포 시간대 | 회의에서 확정되지 않음. 운영 담당자가 서비스 영향과 대응 가능 시간을 고려해 정해야 함 |
| 정기 배포 빈도 | 미정 |
| 앱 공개 빈도 | 스토어 심사와 출시 계획에 따라 결정. 고정 주기 미정 |
| 서버 배포 빈도 | 미정 |
| 허용 가능한 서비스 중단 시간 | 회의에서 확정되지 않음 |
| 무중단 배포 여부 | 인프라 구조 미확정. 보장할 수 없음 |
| 배포 승인자 | 역할·이름 미정 |
| 배포 공지 방식 | 사용자 대상 공개일을 심사 통과 후 결정. 내부 공지 경로 미정 |

## 7. 데이터베이스 변경 및 마이그레이션

실제 데이터베이스 제품과 마이그레이션 도구, 스크립트 이름은 확정되지 않았습니다. 다음 절차는 데이터 변경이 필요한 경우의 **안전 기준**입니다.

### 7.1 변경 전

- 개발·스테이징에서 같은 변경을 먼저 실행합니다.
- 기존 기록에서 음식명·영양값 스냅샷이 보존되는지 확인합니다.
- 영양값 없음과 실제 값 0을 구분하는 자료 형식이 유지되는지 확인합니다.
- 사용자별 소유권과 계정 삭제 연결이 깨지지 않는지 확인합니다.
- 날짜·시간대 변경이 과거 섭취 날짜를 자동으로 바꾸지 않는지 확인합니다.
- 프로덕션 변경 전 데이터베이스 백업이 완료됐는지 확인합니다.
- 되돌리기 어려운 자료 변경은 별도 검토하고 승인 없이 실행하지 않습니다.

### 7.2 마이그레이션 실행

마이그레이션 실행 명령은 미정입니다. 실제 도구가 저장소에 등록되어 있는지 확인한 뒤 사용합니다.

```bash
# 실제 프로젝트 명령 확인
cat package.json
ls -la
```

```bash
# 다음 명령은 형태 예시이며, 실제 등록 여부를 확인해야 함
npm run db:migrate:status
npm run db:migrate
```

마이그레이션 도구가 별도인 경우 해당 도구의 프로젝트별 절차를 사용합니다. 명령이 존재하지 않는 상태에서 예시를 그대로 실행하지 않습니다.

### 7.3 변경 후

- 데이터베이스 변경 상태와 앱·서버 버전의 호환 여부를 확인합니다.
- 식사 기록 조회·수정·삭제를 시험합니다.
- 과거 기록의 이름·영양값 스냅샷이 변경되지 않았는지 확인합니다.
- 기록이 없는 날짜와 영양값이 없는 기록이 0으로 변환되지 않았는지 확인합니다.
- 주간 리포트 계산이 기록된 날 기준으로 동작하는지 확인합니다.
- 계정 삭제 흐름과 사용자별 자료 분리가 유지되는지 확인합니다.
- 서버 오류율, 응답 시간, 저장 실패율이 배포 전후로 악화되지 않았는지 확인합니다.

## 8. 배포 후 점검

회의에서 헬스체크 경로와 실제 점검 도구는 정해지지 않았습니다. 다음은 배포 뒤 수행할 **점검안**입니다.

### 8.1 헬스체크

`/health` 또는 `/api/health` 경로는 회의에서 확정되지 않았습니다. 서버 구현에 해당 경로가 실제 제공되는지 확인하고, 없다면 개인정보를 포함하지 않는 헬스체크 경로를 별도 정의해야 합니다.

```bash
# 실제 헬스체크 경로와 주소는 추정 필요
curl --fail --silent --show-error \
  https://<실제_API_주소>/<실제_헬스체크_경로>
```

예상 응답 형식은 미정입니다. 상태 코드가 성공이고, 응답 본문에 음식명·사용자 자료·비밀값이 포함되지 않는지 확인합니다.

### 8.2 배포 후 점검 목록

| 점검 항목 | 확인 방법 | 기대 결과 |
|---|---|---|
| 서버 기동 | 배포 플랫폼의 서비스 상태 확인 | 서비스가 실행 중 |
| API 응답 | 헬스체크 또는 승인된 점검 경로 호출 | 정상 응답 |
| 데이터베이스 연결 | 서버 진단 자료와 기능 시험 | 연결 오류 없음 |
| 환경 구분 | 앱 빌드와 API 주소 확인 | 출시 빌드는 프로덕션 API 연결 |
| 음식 검색 | 검색 성공·결과 없음·공급자 오류 확인 | 결과 없음과 장애가 구분됨 |
| 직접 입력 | 영양값 없이 음식 저장 | 기록은 저장되고 영양값은 미입력으로 유지 |
| 기록 저장 | 항목 생성 후 조회 | 저장한 내용이 다시 표시됨 |
| 중복 방지 | 저장 요청 재시도 | 같은 요청이 중복 생성되지 않음 |
| 수정·삭제 | 기록 수정 및 삭제 | 화면·리포트에서 변경이 반영됨 |
| 주간 리포트 | 완료된 주와 미기록 날짜 확인 | 기록 일수·평균 기준이 일관됨 |
| 푸시 동의 | 알림 기본 설정과 권한 거부 확인 | 선택하지 않은 사용자에게 발송하지 않음 |
| 개인정보 로그 | 오류 로그와 분석 이벤트 점검 | 식사 내용·체중 등이 포함되지 않음 |
| 계정 삭제 | 시험 계정 삭제 흐름 점검 | 계정·연관 기록의 삭제 처리 상태가 확인됨 |
| TLS 인증서 | 브라우저 또는 시스템 검사 | 유효한 암호화 연결 |
| 비용 알림 | 클라우드·외부 API 사용량 설정 확인 | 사용량 감시가 동작함 |
| 백업·복구 | 백업 결과와 복구 시험 기록 확인 | 백업 자료로 복구가 가능함 |

헬스체크, 서버 오류율, 응답 시간, 저장 실패율의 임계값과 알림 전달 채널은 확정되지 않았습니다. 운영 규모와 베타 자료를 확인한 뒤 기준을 정합니다. 예시 문서에 있던 수치 임계값을 이 서비스의 확정 목표로 적용하지 않습니다.

### 8.3 베타·출시 후 관찰 항목

- 주요 식사 기록 흐름 완료 여부
- 검색 결과 없음 이후 직접 입력으로 이어지는지
- 식사 기록 저장 실패 및 중복 저장 발생 여부
- 주간 리포트가 기록된 내용 기준으로 계산되는지
- iOS·안드로이드 기기별 화면 깨짐과 앱 충돌
- 푸시 동의·권한 거부·알림 해제 동작
- 계정 삭제와 자료 삭제 요청 처리
- 외부 음식 API 호출량과 비용
- 서버 응답 시간, 오류율, 저장 실패율
- 제품 분석 이벤트에 음식명·칼로리·체중이 포함되지 않는지

출시 후 지표는 표본 크기와 사용자 인터뷰·관찰 결과를 함께 보고 해석합니다. 베타 지표만으로 전체 사용자 행동을 단정하지 않습니다.

## 9. 롤백 절차

서버 배포 플랫폼, 앱 배포 방식, 데이터베이스 변경 도구가 미정이므로 특정 도구 명령으로 롤백 절차를 확정할 수 없습니다. 아래는 환경과 기능별로 적용할 **롤백 운영안**입니다.

### 9.1 롤백을 검토할 상황

다음 상황이 발생하면 우선 영향 범위를 확인하고, 사용자가 기록을 잃거나 개인정보가 노출될 위험이 있으면 기능 확장보다 서비스 안정화와 롤백을 먼저 검토합니다.

- 앱 또는 서버가 반복적으로 기동하지 않음
- 핵심 식사 기록 저장·조회가 정상 동작하지 않음
- 중복 기록 또는 치명적인 자료 유실이 확인됨
- 사용자별 자료가 분리되지 않거나 다른 사용자에게 노출될 가능성이 있음
- 오류 로그·제품 분석에 식사 기록이나 체중이 포함되는 문제가 확인됨
- 외부 음식 검색 장애가 직접 입력과 기록 흐름까지 막음
- 계정 삭제 또는 관련 기록 삭제 흐름이 잘못 동작함
- 데이터베이스 변경으로 기존 기록이나 주간 리포트가 손상됨
- 비용 또는 외부 API 호출이 예상보다 증가해 서비스 운영 위험이 발생함

### 9.2 서버 롤백

1. 배포를 담당하는 운영 담당자에게 장애를 알립니다.
2. 장애 발생 시각, 환경, 서버 버전, 앱 버전, 요청 ID, 오류 코드 등 비민감 진단 정보를 확인합니다.
3. 프로덕션 로그에서 음식명·칼로리·체중·자유 입력 내용이 출력되지 않았는지 함께 확인합니다.
4. 변경 전 승인된 서버 버전으로 되돌릴 수 있는지 확인합니다.
5. 데이터베이스 변경이 있었다면 되돌리기 스크립트가 있는지, 실행이 자료 손실을 일으키지 않는지 먼저 확인합니다.
6. 위험이 확인되면 데이터베이스 복구 책임자가 백업과 복구 시점을 검토한 뒤 승인된 복구 절차를 진행합니다.
7. 헬스체크, 로그인, 음식 검색, 직접 입력, 기록 생성·수정·삭제, 리포트 조회를 다시 확인합니다.
8. 장애 원인과 조치 결과를 기록하고 재배포 여부를 결정합니다.

컨테이너 기반 배포를 실제 채택한 경우의 명령 형식 예시는 다음과 같습니다. 이미지 이름, 버전, 배포 설정은 추정 필요이며 실제 배포 환경이 확정된 후에만 사용합니다.

```bash
# 예시: 이전에 승인된 버전으로 이미지를 지정해 재배포
docker compose --env-file <환경_설정_경로> \
  pull <서비스명>

docker compose --env-file <환경_설정_경로> \
  up -d <서비스명>

docker compose ps
```

> 이 명령은 Docker Compose 사용이 확정됐다는 뜻이 아닙니다. 실제 운영 플랫폼에 맞는 롤백 절차를 별도로 마련해야 합니다.

### 9.3 모바일 앱 롤백

모바일 앱은 서버처럼 사용자 기기에 설치된 빌드를 즉시 되돌릴 수 없습니다. 스토어에서 이전 빌드로 되돌리는 것이 가능한지와 절차는 플랫폼 정책 및 배포 도구를 확인해야 합니다.

- 심사 전 문제를 발견하면 해당 빌드 제출 또는 공개를 중단합니다.
- 베타에서 문제를 발견하면 새 수정 빌드를 배포하고, 시험 참여자에게 사용 중지 또는 업데이트 안내가 필요한지 결정합니다.
- 공개 후 문제가 발견되면 서버 측에서 안전하게 제한할 수 있는 기능인지 확인합니다. 기능 제한 장치가 구현돼 있지 않다면 이를 사용할 수 있다고 가정하지 않습니다.
- 서버 API 변경은 구버전 앱과 호환되는지 확인합니다. API 호환성이 확인되지 않으면 앱 수정 빌드와 서버 변경을 함께 계획합니다.
- 공개 일정은 스토어 심사 결과를 확인한 뒤 결정하며, 심사 전 공개를 보장하지 않습니다.

### 9.4 데이터베이스 롤백 주의사항

- 데이터베이스 변경을 되돌릴 때 기록 삭제나 영양 스냅샷 손실이 발생하지 않는지 확인합니다.
- 구조 변경과 자료 변환을 한 번에 되돌릴 수 있는지 스테이징에서 시험합니다.
- 백업 복구는 복구할 시점과 그 이후 생성된 기록의 영향까지 확인합니다.
- 백업은 자동화·암호화·접근 제한을 적용하고 출시 전에 최소 한 번 복구 시험을 수행해야 합니다.
- 백업에서의 완전 삭제 시점과 보존 기간은 미정입니다. 임의의 기간을 문서에 확정하지 말고 법무·개인정보 담당 확인 후 정책에 반영합니다.

### 9.5 롤백 시간

롤백 완료 시간은 회의에서 정해지지 않았으며, **추정 필요**입니다. 다음 항목을 실제 환경에서 시험한 뒤 목표를 정합니다.

- 이전 서버 버전으로 복귀하는 데 걸리는 시간
- 데이터베이스 복구가 필요한 경우의 소요 시간
- 앱 수정 빌드 제작·시험·심사에 필요한 시간
- 담당자 승인과 연락에 걸리는 시간
- 사용자에게 장애나 조치를 안내하는 데 걸리는 시간

## 10. 모니터링 및 알림

모니터링 도구와 알림 채널은 회의에서 확정되지 않았습니다. 도구 선택은 비용, 데이터 처리 위치, 개인정보 보호 조건을 확인한 뒤 진행합니다.

### 10.1 모니터링 대상

| 대상 | 확인 항목 | 자료 제한 |
|---|---|---|
| 서버 안정성 | 서버 상태, 오류율, 응답 시간 | 요청 본문과 식사 내용은 수집하지 않음 |
| 기록 저장 | 저장 성공·실패, 재시도, 중복 방지 결과 | 음식명·영양값은 진단 로그에 포함하지 않음 |
| 음식 검색 | 응답 결과 있음·없음, 공급자 오류, 응답 시간 | 검색어는 제품 분석 이벤트에 저장하지 않음 |
| 외부 공급자 비용 | 호출량, 제한 도달 여부, 비용 사용량 | 사용자 식별 정보나 기록 자료 전달 금지 |
| 앱 상태 | 앱 버전, 플랫폼, 오류 코드, 충돌 여부 | 오류 자료에 음식명·자유 입력 내용 자동 첨부 금지 |
| 푸시 | 토큰 등록·해제, 사용자 설정, 발송 결과 | 푸시 본문에 개인 건강 정보 포함 금지 |
| 데이터베이스 | 연결 상태, 저장 오류, 백업 성공 여부 | 운영자 자료 접근은 권한과 접근 기록 관리 필요 |
| 제품 분석 | 가입 완료, 기록 완료, 검색 결과 유무, 리포트 열람 등 | 선택 동의 대상. 음식명·칼로리·체중 제외 |
| 비용 | 서버·외부 API·저장소 사용량 | 실제 예산 한도는 계약과 견적 확인 후 결정 |

### 10.2 로그 기록 기준

허용할 수 있는 진단 정보의 예시는 다음과 같습니다.

- 앱 버전
- 플랫폼과 기기 종류
- 오류 코드
- 요청 식별값
- 오류 발생 시각
- 서버 구성요소와 처리 단계
- 제품 분석을 위한 최소 행동 이벤트

로그·분석 자료에 포함하지 않을 정보:

- 음식명 및 검색어 자체
- 칼로리·탄수화물·단백질·지방 값
- 체중, 키, 생년월일 등 프로필 정보
- 자유 입력 내용
- 인증 토큰, 비밀번호, 외부 API 자격 증명
- 식사 기록의 전체 요청·응답 본문
- 푸시 토큰 등 별도 보호가 필요한 식별값

운영자가 사용자 식사 기록을 확인해야 하는 경우에는 사용자 동의와 권한 승인을 거치고 접근 기록을 남깁니다. 관리자 화면이 없는 상태에서 운영자가 임의로 전체 기록을 열람하는 구조를 만들지 않습니다.

### 10.3 알림 기준과 연락 경로

알림 조건, 임계값, 전달 채널, 담당자는 회의에서 확정되지 않았습니다. 운영팀은 실제 사용 자료와 대응 가능 시간을 확인한 뒤 정해야 합니다.

| 알림 대상 | 제안 조건 | 현재 상태 |
|---|---|---|
| 서비스 이용 불가 | 헬스체크 실패가 확인될 때 | 상태 확인 경로·알림 채널 추정 필요 |
| 서버 오류 증가 | 기준 대비 오류 증가가 확인될 때 | 수치 기준 추정 필요 |
| 응답 지연 | 서비스 응답 시간이 운영 기준을 넘을 때 | 임계값 추정 필요 |
| 저장 실패 증가 | 식사 기록 저장 실패가 기준을 넘을 때 | 수치 기준 추정 필요. 우선 점검 대상 |
| 외부 음식 API 장애 | 공급자 오류 또는 호출 제한 초과 | 계약상 제한·알림 방식 확인 필요 |
| 비용 증가 | 서버·외부 API 사용량이 설정한 알림 기준에 도달할 때 | 견적과 예산 승인 절차 확정 필요 |
| 백업 실패 | 자동 백업 실패 또는 복구 시험 실패 | 보관 위치·실패 알림 방식 추정 필요 |
| 인증서 만료 임박 | API 도메인 인증서 만료 전 | 도메인·인증서 관리 방식 추정 필요 |

회의에서 베타 초기 월 운영 비용 30만 원 안쪽이 검토 기준으로 언급됐으나, 절대 한도는 아니며 API 계약과 품질을 확인한 뒤 재검토하기로 했습니다. 이를 확정 예산이나 자동 차단 기준으로 사용하지 않습니다.

## 11. 보안 설정

### 11.1 통신·접근 보호

- 앱과 서버 사이의 통신은 HTTPS를 사용합니다.
- 데이터베이스는 공용 인터넷에 직접 노출하지 않는 구성을 검토합니다.
- 서버·데이터베이스·클라우드 관리 권한은 업무상 필요한 담당자에게만 부여합니다.
- 개발·스테이징·프로덕션 자격 증명을 분리합니다.
- 사용자별 음식·기록 자료는 인증된 사용자 소유 여부를 확인한 뒤 접근하도록 구현합니다.
- 원문 비밀번호를 저장하지 않습니다. 인증 제공자 또는 검토된 인증 구조를 사용합니다.
- 운영자가 사용자 기록을 열람하는 경우 동의, 권한 승인, 접근 기록을 요구합니다.
- 앱 자체 잠금·생체 인증은 MVP에서 제외하는 결정이 확인됐습니다. 네트워크 전송 암호화와 데이터 접근 권한 제한을 우선합니다.

### 11.2 개인정보·외부 업체 보호

- 주소록과 위치 정보는 수집하지 않습니다.
- 외부 식품 API에는 검색어만 전달하고 사용자 ID, 이메일, 기록 날짜, 식사 기록은 보내지 않는 방향입니다.
- 검색어가 외부 업체에 전달될 수 있으므로 보관 조건, 처리 위치, 이용 조건, 캐시 허용 범위, 계약 내용을 출시 전에 확인합니다.
- 분석 이벤트에는 음식명과 칼로리를 포함하지 않습니다. 체중과 자유 입력 내용도 제품 분석에 포함하지 않습니다.
- 선택적 제품 분석은 사용자가 거부할 수 있게 하고, 거부해도 기록 기능은 정상 작동해야 합니다.
- 제품 분석과 보안·장애 대응을 위한 최소 로그를 분리합니다.
- 외부 분석·푸시 업체의 데이터 처리 위치와 국외 이전 여부를 확인하고, 확인된 내용을 개인정보 안내와 동의 흐름에 반영합니다.
- 사진 기능은 회의 결정에서 제외와 포함 내용이 상충합니다. 사진 기능을 출시 범위에 포함하기 전 저장 위치, EXIF 처리, 비공개 접근, 보관·삭제 조건을 확정해야 합니다. 사진 자동 분석은 MVP 필수 기능으로 확정되지 않았습니다.
- 계정 삭제 요청 시 계정과 연관 기록을 삭제하는 흐름을 구현합니다. 백업에서의 삭제 완료 시점, 보관 기간 및 법적 보관 의무는 별도 확인이 필요합니다.
- 장기 미사용 계정 자동 삭제는 정책이 확정되기 전까지 구현하지 않는 방향입니다.

### 11.3 비밀값·앱 서명 보호

- iOS 서명 자격 증명, 안드로이드 서명 키, 인증 제공자 비밀값, 음식 API 키, 데이터베이스 접속 정보는 저장소에 올리지 않습니다.
- 운영 비밀값을 개발자 개인 장비나 공용 문서에 장기간 보관하지 않습니다.
- 앱에 포함되는 값과 서버에서만 사용해야 하는 비밀값을 분리합니다.
- 서명 자격 증명의 접근 권한과 보관 위치, 분실·교체 절차를 사전에 정합니다.
- 스토어 등록 권한은 개발팀이 필요한 범위에서 사용할 수 있게 분리합니다. 회의에서 회사 계정의 신규 앱 등록 권한 보유자를 확인하기로 했습니다.
- 프로덕션 배포 전에는 배포 대상 커밋, 앱 버전, 서명 설정, API 주소, 데이터베이스 변경을 함께 검토합니다.

### 11.4 방화벽과 서버 보호

서버 운영 방식과 네트워크 구성이 정해지지 않아 방화벽 명령이나 포트 목록을 확정할 수 없습니다. 실제 서버 구성 확정 후 다음 원칙을 적용합니다.

- 외부 공개가 필요한 API 통신만 허용합니다.
- 데이터베이스와 내부 관리 도구는 외부에 직접 공개하지 않습니다.
- 서버 관리 접속은 승인된 경로와 계정으로 제한합니다.
- 운영 환경에 사용하지 않는 포트와 서비스를 닫습니다.
- 외부 공급자 호출과 푸시 전달에 필요한 통신만 허용하는 방안을 검토합니다.
- 설정 변경 후 앱의 검색·기록·푸시 기능과 헬스체크를 다시 확인합니다.

### 11.5 출시 전 보안 점검표

- [ ] 프로덕션 API 주소와 HTTPS 연결 확인
- [ ] 개발·스테이징·프로덕션 자격 증명 분리 확인
- [ ] 인증 제공자와 계정 삭제 흐름 확인
- [ ] 사용자별 기록·개인 음식 접근 제한 확인
- [ ] 외부 음식 API에 사용자 식별 정보·식사 기록이 전달되지 않는지 확인
- [ ] 검색어 보관·처리·캐시 조건과 개인정보 안내 확인
- [ ] 분석 동의가 선택 사항이며 거부해도 기능이 동작하는지 확인
- [ ] 분석 이벤트에 음식명·칼로리·체중이 없는지 확인
