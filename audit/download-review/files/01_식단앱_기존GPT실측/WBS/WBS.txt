2. 프로젝트 개요

2.1 프로젝트 정보

이 프로젝트는 식단을 기록하려다가 입력 부담 때문에 중단하는 국내 일반 사용자를 위해 모바일 식단 기록 앱의 MVP를 만드는 사업입니다. 핵심 목표는 전문적인 영양 상담이나 의학적 권고가 아니라, 음식 검색·최근 기록·즐겨찾기·직접 입력을 통해 식사를 쉽게 기록하고 나중에 다시 확인하도록 돕는 것입니다. iOS와 안드로이드를 함께 지원하며, 크로스플랫폼 개발은 React Native를 사용하는 방향으로 논의됐습니다.

MVP에는 가입·로그인, 선택적 목표 설정, 오늘 홈, 음식 검색, 최근 기록, 즐겨찾기, 직접 음식 입력, 식사 기록의 생성·수정·삭제, 날짜별 조회, 기본 주간 리포트, 선택형 기록 알림, 개인정보·계정 설정 및 계정 삭제 흐름이 포함됩니다. 영양 정보는 참고값으로 안내하고, 정보가 없는 음식도 기록할 수 있어야 합니다. 외부 식품 데이터가 바뀌더라도 과거 기록에 저장된 음식 이름과 영양값은 자동으로 변경되지 않도록 합니다.

프로젝트 일정은 8주를 기준으로 운영합니다. 8주 차에는 출시 후보 빌드와 스토어 심사 제출을 목표로 하며, 실제 공개일은 베타 결과와 심사 통과 후 확정합니다. 스토어 심사 지연에 대비해 9주 차를 완충 기간으로 둡니다. 기능 동결은 6주 차 초를 목표로 하고, 이후에는 신규 기능보다 결함 수정과 안정화를 우선합니다.

성공 기준은 사용자가 첫 식사를 쉽게 기록하고, 홈에서 오늘의 기록 상태를 확인하며, 완료된 주의 기록을 주간 리포트에서 다시 보는 핵심 흐름을 구현하는 것입니다. 베타에서는 첫 기록 완료율, 기록 완료 시간, 주간 기록 일수, 검색 실패 후 이탈, 직접 입력 비율, 리포트 열람률 등을 기준선 확인 용도로 살펴봅니다. 회의에서 언급된 수치 목표는 검증 가설 또는 시험 제안이므로, 별도 승인 전까지 확정 성능 기준으로 사용하지 않습니다.

주요 이해관계자는 사업 책임자인 이대표, 프로젝트 관리와 요구사항·테스트를 맡는 김PM, 화면 설계와 사용성 검증을 맡는 박디자이너, 앱·서버·외부 연동 기술 검토를 맡는 최개발입니다. 외부 식품 데이터 공급자, 법무·개인정보 담당, 보안 검토자, 사용자 조사·베타 참여자도 협업 대상입니다. 전담 QA 인력은 확보되지 않은 것으로 논의됐으며, 앱 개발 지원 인력은 배정 여부 확인이 필요합니다.

2.3 가정 및 제약사항

가정사항

☐ 회의 참여 역할을 맡은 인력은 프로젝트 수행 가능 여부를 확인한 뒤 배정됩니다. 실제 배정과 참여율은 추정 필요입니다.
☐ 외부 식품 API 또는 대체 데이터의 샘플과 계약 조건이 일정 내 확인된다고 가정하지 않습니다. 확인 전에는 임시 시험 자료로 개발할 수 있도록 계획합니다.
☐ API 공급처는 1주 차 금요일까지 샘플·계약 조건을 확인하고, 2주 차 화요일까지 미정이면 일정 위험으로 올립니다.
☐ 로그인 제공자 범위는 이번 주 체크포인트에서 검토하고, 다음 주 화요일까지 확정하는 것을 목표로 합니다.
☐ 자동 권장 칼로리 안전 기준을 다음 주 화요일까지 확인하지 못하면 자동 칼로리 목표를 MVP에서 제외합니다.
☐ 사진 자동 인식은 1주 차 금요일 기술 검증 후 별도 판단하며, 핵심 기록 기능이나 일정에 영향을 주면 제외합니다.
☐ 디자인과 개발은 순차 전달을 활용해 병렬 진행할 수 있습니다.
☐ 베타 모집 규모는 회의에서 여러 안이 제시됐으므로 최종 모집 인원과 운영 방식은 별도로 확정합니다.
☐ 외부 법무·개인정보·전문가 검토의 회신 일정은 확정되지 않았으며, 검토 지연 시 범위 축소 판단이 필요합니다.
☐ 스토어 계정과 신규 앱 등록 권한이 준비됐는지 확인이 필요합니다.

제약사항

☐ 일정은 8주 내 출시 후보 빌드와 심사 제출을 목표로 하며, 실제 공개는 스토어 심사 결과에 따라 9주 차 이후가 될 수 있습니다.
☐ 주요 기능 동결 목표는 6주 차 초입니다.
☐ 전담 QA 인력은 없는 것으로 회의에서 공유됐으며, PM·디자이너·개발자가 검증을 나눠 맡아야 합니다.
☐ 개발 지원 인력 배정 여부가 미확정이며, 앱 화면 개발 안정성에 영향을 줄 수 있습니다.
☐ 인증 제공자, 식품 데이터 공급처, API 호출·캐시 계약, 일부 개인정보 정책이 미확정입니다.
☐ 개인정보는 최소 수집하고, 음식명·칼로리·체중·자유 입력 내용은 제품 분석 및 일반 오류 기록에 포함하지 않는 방향으로 설계합니다.
☐ 외부 식품 API에는 검색어만 전달하고 사용자 식별 정보·기록 날짜·식사 기록은 전달하지 않는 방향입니다.
☐ 월 30만 원은 검토용 예시이며 확정 예산 한도가 아닙니다. 사용자 수별 서버·API 비용 추정이 필요합니다.

· 요구사항과 기술 조사, 화면 설계를 W1부터 병렬로 진행합니다.
· W2 말까지 핵심 화면과 데이터·API 골격을 확정한 뒤 W3부터 검색·기록 본개발을 진행합니다.
· W6 초 기능 동결 뒤 통합 시험과 결함 수정에 집중합니다.
· 베타 빌드는 W7 초반, 스토어 제출은 W7 말 목표로 배치합니다.
· 공개는 심사 결과 전 확정하지 않으며 W9를 완충으로 둡니다.
· 식품 API가 W2 화요일까지 미정이면 출시 위험으로 상향하고, 임시 자료 개발과 범위 축소 여부를 결정합니다.
· 자동 칼로리 목표의 안전 기준을 정해진 확인 시점까지 확보하지 못하면 해당 기능을 제외합니다.
· 사진 첨부는 포함·제외 결정이 상충하므로 승인 전 핵심 일정의 선행 조건으로 두지 않습니다.

의존 관계 해석

· FS(완료 후 시작): 선행 작업의 완료 후 후속 작업을 시작합니다.
· SS(동시 시작): 선행 작업이 시작되면 후속 작업을 병행할 수 있습니다. 단, 결과물 확정 전에는 실제 연동·화면 고정을 제한합니다.
· FF(동시 완료): 관련 작업이 같은 완료 시점까지 마무리돼야 합니다.
· SF(시작 후 완료): 선행 작업의 시작을 기준으로 후속 작업을 완료하는 관계입니다. 본 계획에는 적용되는 작업이 없습니다.
· 사진 첨부: 최종 범위 승인과 삭제·저장 정책 확인 전에는 개발 착수를 진행하지 않는 FS 관계입니다.
· 공개 일정: 스토어 심사 완료가 공개 결정의 선행 조건이며, W8 내 실제 공개를 보장하지 않습니다.
