4. 스토리보드 시트

표정과 생각은 실제 조사 결과가 아니라 사용 경험을 구체적으로 그리기 위한 가상 예시입니다. 화면 요소는 회의에서 합의된 원칙과 기능을 중심으로 작성했으며, 세부 배치와 문구는 디자인 검토 대상입니다.

장면 1: 기록을 포기했던 경험을 떠올림

화면 묘사
점심 식사를 마친 사용자가 휴대전화에서 식단 기록 앱을 열었다가, 여러 음식을 하나씩 입력해야 하는 화면을 보고 망설입니다. 음식 이름과 양을 정확히 모르는 상황에서 입력이 번거롭게 느껴져 기록을 미루거나 중단한 경험이 있습니다.

요소 분석

요소	상세 내용
배경	점심시간 직후의 사무실 또는 식사 장소. 정확한 장소와 시간은 가정
사용자 상태	식사를 마친 상태로 휴대전화를 바라봄. 여러 메뉴를 떠올리려다 입력 화면에서 잠시 멈춤
행동	음식 이름과 양을 입력하려다가 앱을 닫거나 기록을 미룸
생각·대사	“밥이랑 반찬을 다 적으려면 너무 오래 걸릴 것 같은데.” — 가상 예시
감정	😟 부담과 피로. 기록을 시작하려는 마음은 있으나 입력량에 압도됨
페인 포인트	메뉴가 여러 개면 입력량이 늘어남. 양과 영양값을 모를 때 기록을 완성하기 어려움
감정 변화	기록 의향 → 입력 부담 인식 → 미루거나 중단

UI 요소

· 현재 화면: 기존에 사용하던 식단 앱 또는 수기 메모 화면 — 실제 사용 앱과 화면은 추정 필요
· 문제 요소: 한 끼를 음식별로 기록하는 수고, 영양값을 알고 입력해야 할 것 같은 부담
· 스토리보드 제안: 이 장면에서는 신규 앱의 기능을 보여주기보다, 기록 부담이 발생하는 순간을 시각화합니다.

장면 2: 기록을 그만둔 이유를 돌아봄

화면 묘사
사용자는 과거에 식단 앱을 사용하다 중단했던 경험을 떠올립니다. 정확한 기록을 위해 음식과 양을 계속 입력해야 했고, 검색 결과가 없거나 식사 구성이 복잡하면 기록을 끝내기 어려웠습니다.

장면 5: 가입하거나 앱을 시작하는 방법을 선택함

화면 묘사
사용자는 앱을 시작하려 하지만, 계정 생성이 먼저 필요한지 궁금해합니다. 게스트 시작과 이메일·애플·구글 인증이 논의됐으나 최종 방식은 확정되지 않았으므로, 화면 구성과 실제 선택지는 정책 확정 후 결정해야 합니다.

장면 7: 음식 검색과 직접 입력으로 첫 식사를 기록함

화면 묘사
사용자는 홈에서 식사 구분을 선택한 뒤 음식을 추가합니다. 검색 결과가 있으면 직접 확인해 선택하고, 결과가 없거나 외부 API가 실패하면 직접 입력으로 전환합니다. 음식명만으로도 저장할 수 있으며 영양 정보는 참고값으로 다룹니다.

요소 분석

요소	상세 내용
배경	집이나 직장 등 사용자가 식사를 마친 장소 — 구체적인 장소와 시각은 가정

· 저장 상태: 저장 중·완료·실패를 구분. 실패 시 입력값을 유지하고 재시도 안내
· 제외 범위: 메모, 그램 환산, 자유 형식 단위 입력, 사진 자동 인식, 바코드

7. UI 시나리오

시나리오 1: 목표 없이 시작해 첫 기록 남기기

화면별 상세 흐름

1. 사용자가 앱을 처음 실행함.
2. 시작 화면에서 앱의 핵심 목적을 확인함: 식사를 쉽게 기록하고 기록된 내용을 다시 확인.
3. 동의 화면에서 서비스 이용약관과 개인정보 처리 안내를 확인함. 푸시 선택은 약관 동의와 분리됨.
4. 계정 화면에서 확정된 인증 또는 게스트 방식이 제공되면 원하는 방식을 선택함. 실제 선택지는 계정 정책 확정 후 결정.
5. 온보딩에서 식사 습관 확인·체중 목표 설정·목표 없이 기록 중 하나를 선택함.
6. 사용자가 목표 없이 기록을 선택함. 키·체중·나이·성별을 필수로 입력하지 않음.
7. 앱이 홈으로 이동함. 오늘 기록 상태와 식사 구분별 기록 동작을 확인함.
8. 사용자가 식사 구분을 선택하고 음식 추가 화면으로 이동함.
9. 검색·최근·즐겨찾기·직접 입력 중 하나를 선택함. 기본 탭은 미확정.
10. 사용자가 음식을 선택하거나 직접 음식명을 입력함. 영양값이 없더라도 저장 가능.
11. 사용자가 양과 식사 구분을 확인하고 저장함.
12. 저장 완료 상태와 홈의 기록 반영 여부를 확인함.

화면 전환 수: 정확한 수는 화면 설계 이후 산정 필요
예상 소요 시간: 확정된 시간 기준 없음. 첫 실행 후 첫 기록을 2분 안에 완료하는 비율 75% 이상은 회의에서 검증 가설로 제시됐으나, 후속 논의에서는 베타 지표의 수치 목표를 미리 고정하지 않고 기준선을 확보하기로 함.

시나리오 2: 여러 음식 항목을 한 식사 구분에 기록하기

1. 사용자가 홈에서 기록 날짜를 확인함.
2. 아침·점심·저녁·간식 중 해당 식사 구분을 선택함.
3. 음식 추가 화면에서 검색을 하거나 최근 기록·즐겨찾기를 선택함.
4. 검색 결과가 있으면 사용자가 직접 항목을 고름. 앱은 부정확한 결과를 자동 선택하지 않음.
5. 검색 데이터에 기준 제공량이 있으면 표시하고, 사용자가 배수로 양을 조정함.
6. 사용자가 항목을 저장함. 각 항목은 개별 저장됨.
7. 같은 식사 구분에 음식이 더 있으면 추가로 기록함.
8. 홈에서 같은 날짜와 식사 구분의 항목 목록과 합계를 확인함.
9. 영양 정보가 없는 음식은 기록 목록에 남고, 해당 영양소 합계에서는 제외됨.
10. 필요하면 기록을 수정하거나 개별 삭제함.

화면 전환 수: 설계 확정 후 산정 필요
예상 소요 시간: 확정된 기준 없음. 기록 완료 시간을 베타에서 관찰·측정할 계획

시나리오 3: 주간 리포트를 확인하고 기록을 이해하기

1. 사용자가 주간 리포트 화면을 엶.
2. 앱이 한국 시간 기준으로 완료된 주의 기록을 불러옴.
3. 사용자가 7일 중 기록한 일수를 확인함.
4. 기록이 있는 날 기준으로 계산한 평균 칼로리와 영양값을 확인함.
5. 목표를 설정한 경우에만 해당 기간에 적용되는 목표와 비교함.
6. 끼니별 기록 패턴을 확인함.
7. 기록이 없는 날은 0이 아닌 빈칸이나 점선 등으로 확인함.
8. 일부 음식 정보가 없으면 영양소별 합계가 달라질 수 있다는 안내를 확인함.
9. 데이터가 충분한 경우에만 보조 비교가 표시됨. 비교를 위한 최소 기록 기준은 미정.

화면 전환 수: 정확한 수는 설계 후 산정 필요
예상 소요 시간: 확정된 기준 없음

시나리오 4: 검색 결과 없음 또는 저장 오류에서 복구하기

1. 사용자가 음식 검색어를 입력함.
2. 앱이 검색 요청을 보내고 검색 결과·결과 없음·오류 상태를 구분함.
3. 검색 결과가 없으면 직접 입력을 안내함.
4. 외부 API 오류나 네트워크 오류면 검색어를 유지하고 재시도 또는 직접 입력을 제공함.
5. 사용자가 직접 음식명을 입력함. 영양 정보는 선택 입력.
6. 저장이 실패하면 입력 내용을 유지하고 실패 상태를 표시함.
7. 사용자가 재시도를 선택함.
8. 요청 ID를 사용해 중복 저장을 방지하는 방향을 검토함.
9. 저장 성공 여부가 확인된 뒤에만 기록을 완료 상태로 표시함.

화면 전환 수: 정확한 수는 설계 후 산정 필요
복구 정책: 임시 보존 범위와 재시도 방식은 기술 난이도 확인 필요

10. 메트릭

베타 지표는 우선 사용 현황의 기준선을 확보하기 위한 것입니다. 후속 논의에서 사전에 수치 목표를 고정하기보다, 적은 표본에서 발생할 수 있는 편차를 고려해 인터뷰와 관찰 결과를 함께 보자는 방향이 정리됐습니다. 회의에서 나온 첫 실행 후 첫 기록을 2분 이내 완료하는 비율 75% 이상은 검증 가설로 제시됐으나, 확정 KPI로 간주하지 않습니다.

분석 수집 원칙

· 선택적 제품 분석을 거부해도 식사 기록 기능은 정상적으로 동작해야 합니다.
· 분석 이벤트에는 가입 완료, 목표 설정 여부, 첫 기록, 검색 실행, 검색 결과 유무, 직접 입력, 리포트 열람 등 필요한 행동 정보만 포함하는 방향입니다.
· 음식명, 칼로리, 몸무게, 자유 입력 메모, 사용자 이메일은 제품 분석 도구로 보내지 않습니다.
· 보안·장애 대응용 최소 로그는 제품 분석과 분리하며, 수집 항목과 보관 정책은 개인정보 담당 확인이 필요합니다.
· 외부 식품 API에는 검색어만 전달하는 방향이며 사용자 식별자·기록 날짜·기록 데이터는 보내지 않습니다. 검색어의 보관 조건과 외부 처리 고지는 공급자 계약 및 법무 검토가 필요합니다.
