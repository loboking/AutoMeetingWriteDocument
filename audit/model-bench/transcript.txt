이대표: 칼로리를 모르는 사람이 대다수일 텐데, 비어 있으면 홈의 합계가 부정확해지죠. 그래도 무조건 입력하라고 할 수는 없으니까요. 이름만 저장하는 기록도 허용해야 합니다.

박디자이너: 그럼 이름만 넣고 저장할 때 “영양 정보 없이 기록할까요?”라고 한 번 안내하면 어때요. 계속 팝업이 뜨면 귀찮으니 처음 한 번 정도만. 입력 후 홈에서는 칼로리 합계에 포함하지 않고, 기록 개수에는 포함하는 거죠.

최개발: DB에는 영양값을 nullable로 저장하면 됩니다. 값이 0인 것과 정보가 없는 걸 구분해야 해요. 칼로리를 모른다고 0으로 넣으면 리포트에서 평균을 잘못 계산합니다. 영양 데이터 출처도 저장하는 게 좋아요. 식품 DB에서 가져온 건지, 사용자가 입력한 건지 구분해야 수정이나 품질 분석이 가능합니다.

김PM: 좋습니다. DB 얘기로 넘어가죠. 예상 테이블이 뭐가 필요할까요? 사용자, 음식 데이터, 사용자 기록, 목표, 알림 설정 정도?

최개발: 최소한 users, food_items, meal_logs, user_settings, goals 정도요. meal_logs에는 사용자 ID, 음식 ID가 있거나 직접 입력 이름, 섭취 날짜와 시간, 식사 타입, 섭취량, 영양 정보 스냅샷, 생성·수정 시각이 들어가야 합니다. 외부 식품 DB의 항목은 나중에 이름이나 영양값이 바뀔 수도 있어서, 기록 당시의 값도 로그에 복사해두는 게 안전해요.

박디자이너: 그럼 음식 데이터가 나중에 바뀌어도 옛날 리포트 숫자는 그대로 유지된다는 거죠?

최개발: 네. 사용자가 3월에 기록한 김밥의 칼로리가 외부 DB 업데이트로 4월에 바뀌어도 과거 기록을 다시 계산해서 덮어쓰면 안 됩니다. 당시 섭취량과 영양 정보 스냅샷을 로그에 남겨야 해요.

김PM: 사용자 삭제 요청이 오면 로그 데이터도 같이 삭제되게 해야 하고요. 계정 자체를 탈퇴해도 기록이 남아 있는 건 안 됩니다.

최개발: 맞습니다. 사용자 계정과 연관된 데이터가 연쇄 삭제되도록 설계할 수 있고, 백업에서 언제 완전히 삭제되는지는 운영 정책도 필요합니다. 앱에서 탈퇴 버튼을 누르는 즉시 서비스 DB에서는 삭제하거나 비식별 처리하고, 백업 보존 기간을 약관과 개인정보 처리방침에 명시해야 합니다.

이대표: 개인정보는 최대한 적게 받읍시다. 주소록이나 위치는 절대 안 받고요. 건강 앱처럼 보인다고 건강 관련 정보를 이것저것 요구하면 부담이 커요. 체중도 선택 입력으로 하죠.

김PM: 체중, 키, 생년월일, 성별은 목표 칼로리 계산에 꼭 필요한지 검토하고, 꼭 필요한 최소 항목만 받는 걸로. 생년월일 대신 연령대 입력이 가능한가요?

최개발: 계산 정확도는 생년월일이 더 낫지만, 목표 칼로리는 참고값이라고 하면 연령대만으로도 충분할 수 있습니다. 성별 입력을 필수로 둘 필요도 없고요. 다만 계산식에 성별 변수가 들어가면 선택하지 않은 경우 기본값을 임의로 쓰지 말고, 목표 칼로리를 계산하지 않는 게 낫습니다.

박디자이너: 입력 화면에서 성별을 남녀 두 개만 놓는 것도 조심스러워요. “계산에 참고할 신체 정보”라는 맥락을 주고, 건너뛰기를 명확하게 넣어야 할 것 같아요. 아예 키와 체중을 직접 입력해 목표를 정하게 하고, 자동 추천은 나중에 넣을 수도 있어요.

이대표: 좋아요. MVP에서 의학적인 계산을 제공하는 건 아니니까 자동 권장 칼로리도 안 넣어도 됩니다. 사용자가 스스로 하루 목표 숫자를 입력할 수 있으면 충분해요. 다만 나중에는 제휴 전문가 검토를 받고 싶어요.

최개발: 그럼 목표 데이터는 사용자가 정한 일일 칼로리, 탄수화물·단백질·지방 목표를 저장할 수 있게 만들되, 입력 UI는 칼로리만 우선 제공하는 식으로 할 수 있겠네요. 탄단지 목표를 초기에 안 보이게 해도 스키마 확장에 문제 없고요.

김PM: 앱에서는 칼로리뿐 아니라 단백질 정도는 보여주고 싶다는 얘기도 있었는데요. 사용자에게 어떤 숫자를 제공하는 게 적당할까요?

이대표: 일단 총 칼로리하고 단백질. 탄수화물, 지방까지 한 번에 보여주면 초보자는 복잡하다고 느낄 수 있어요. 근데 데이터가 있으면 리포트에서 선택적으로 볼 수는 있겠죠.

박디자이너: 홈에는 칼로리 합계만 간결하게 보여주고, 상세 기록에서 단백질·탄수화물·지방을 볼 수 있게 하면 돼요. 주간 리포트에는 칼로리 평균하고 기록한 날 수, 아침·점심·저녁 중 어떤 식사가 가장 자주 빠졌는지 정도. 숫자를 너무 많이 넣지 않는 게 좋을 것 같아요.

김PM: 리포트 범위가 중요하네요. MVP 리포트에서 어떤 게 반드시 들어가야 한다고 보세요?

이대표: 최소한 지난 7일 동안 기록한 날 수, 하루 평균 칼로리, 목표가 있는 사람은 목표 대비 평균, 그리고 가장 자주 기록한 식사 시간대. 그 정도면 들어올 이유가 생길 것 같아요.

최개발: 기록이 없는 날을 평균에 넣을지 빼야 합니다. 7일 중 3일만 기록했는데 기록된 3일의 평균 칼로리를 “주간 평균”이라고 하면 오해할 수 있어요. “기록한 날 기준 평균”이라고 표기해야 합니다.

박디자이너: 맞아요. 리포트 상단에 “지난 7일 중 4일 기록했어요”를 먼저 보여주고, 평균 칼로리는 “기록한 날 기준”이라고 작은 라벨 붙이죠. 목표 초과나 미달을 평가처럼 쓰지 않고, 패턴을 보여주는 톤으로요.

김PM: 식사 시간대 분석은 음식 기록에 식사 타입이 필수로 있어야겠네요. 아침, 점심, 저녁, 간식. 사용자가 시간을 직접 입력하기보다 구분을 선택하고, 기본값은 현재 시간에 따라 추천하는 건 어때요?

최개발: 가능해요. 오전 5시에서 10시 반이면 아침, 10시 반에서 3시까지 점심, 3시부터 9시까지 저녁 같은 규칙을 둘 수는 있는데, 사람마다 식사 시간이 다릅니다. 아침을 오후에 먹는 사람도 있고 야간 근무도 있어요. 추천만 하고 사용자가 바꿀 수 있게 해야 합니다.

박디자이너: 추천 라벨에 작은 드롭다운을 두고, 저장 전에 한 번 바꿀 수 있으면 되겠네요. 시간을 자동으로 넣고 나중에 식사 구분을 계산할 수도 있지만, 사용자가 “점심”이라고 직접 지정하는 게 리포트에는 더 편할 것 같아요.

이대표: 간식도 있어야 해요. 간식을 기타로 숨기면 사람들이 끼니에 억지로 넣을 것 같아요.

김PM: 네 구분으로 고정하되, 나중에 사용자가 식사 구분을 추가하거나 이름을 바꾸는 기능은 제외. 기록 편집은 허용하고 삭제도 가능. 잘못 입력한 걸 수정할 수 있어야 하니까요.

최개발: 삭제는 즉시 반영하고, 수정 시 이전 값을 감사 로그로 남길 필요가 있는지 확인해야 합니다. 일반 소비자 앱이라 모든 변경 이력을 오래 보관할 필요는 없어 보이지만, 장애 분석 때문에 최소한 서버 로그는 둬야 합니다. 개인정보와 기록 내용이 로그에 찍히지 않게 해야 하고요.

김PM: 외부 API로 넘어가죠. 식품 영양 정보는 어디서 가져오면 좋을까요? 공공데이터포털 식품 영양성분 데이터가 있고, 상용 API도 찾아볼 수 있을 텐데요.

최개발: 공공데이터는 무료인 대신 데이터 포맷이 일정하지 않거나, 상품 바코드 정보가 부족할 수 있어요. 국내 일반 음식 데이터는 꽤 있지만 브랜드 메뉴가 모두 있는 건 아닙니다. API 호출 제한이나 최신 데이터 갱신 주기도 확인해야 합니다. 외부 API를 앱에서 매번 직접 호출하면 키 노출하고 응답 지연 문제가 있으니 서버에서 중계해야 합니다.

이대표: 상용 API는 비용이 얼마예요? 처음부터 월 몇백만 원씩 나가면 안 됩니다.

최개발: 지금 업체별 견적을 확인한 건 아니고요. 요청량 기반이면 초기엔 월 수십만 원에서 시작할 수도 있지만, 이미지 인식까지 붙으면 훨씬 올라갈 수 있습니다. 사용자가 검색할 때마다 외부 호출하지 않고, 데이터를 내부 DB에 캐시하거나 배치로 받아두는 방식으로 비용을 줄일 수 있어요. 계약 조건에 따라 재배포가 가능한지도 봐야 합니다.

김PM: 국내 메뉴 검색이 핵심이라 해외 영양 API 하나만 붙이는 건 별로일 수 있겠네요. 이번 주 안에 공공 데이터와 상용 서비스 두세 곳 비교표를 만들죠. 데이터 범위, 라이선스, 호출 제한, 예상 비용, 업데이트 주기.

박디자이너: 검색 결과가 없는 경우에 사용자가 직접 만든 음식을 저장하고, 다음에 다시 찾을 수 있어야 해요. 그게 API 데이터가 부족한 걸 보완해줄 수 있습니다. 최근 기록과 즐겨찾기만 잘해도 매번 검색할 필요가 줄고요.

최개발: 사용자 지정 음식은 food_items와 분리해서 사용자별 음식 테이블로 두거나, 음식 항목에 소유자 ID를 추가할 수 있어요. 공개 음식과 개인 음식을 명확히 구분해야 하고, 한 사용자가 만든 항목이 다른 사용자 검색 결과에 보이면 안 됩니다. 나중에 커뮤니티 데이터로 공개하려면 별도 동의가 있어야겠죠.

이대표: 사용자 음식 데이터를 회사가 광고나 다른 목적으로 쓰는 건 안 됩니다. 지금은 개인 기록에만 사용하고, 집계 분석을 할 때도 비식별 통계를 기준으로 해야 해요.

김PM: 그 내용은 개인정보 검토 사항에 적어둘게요. 앱 분석 도구도 붙일까요? 가입 완료율, 기록 저장 성공률 같은 건 봐야 하잖아요.

최개발: 분석 SDK를 붙이면 이벤트 이름하고 수집 항목을 정해야 합니다. 음식 이름이나 칼로리 값 같은 실제 건강 기록은 분석 도구로 보내지 않는 게 맞아요. “기록 추가 버튼 클릭”, “검색 결과 없음”, “온보딩 완료” 같은 행동 이벤트만 보내고, 사용자 ID도 가명 처리하거나 내부 식별값과 분리해야 합니다.

박디자이너: 저는 온보딩에서 어느 단계에서 나가는지, 기록 추가 화면에서 검색을 얼마나 하는지 정도는 알고 싶어요. 검색어 자체는 보내지 말고 검색 결과가 있었는지 여부만. 예를 들어 “검색 결과 0건” 이벤트.

이대표: 이 부분은 개인정보 처리방침에 써야겠죠? 데이터 분석한다고 사용자 기록을 들여다보는 것처럼 느끼면 안 돼요.

최개발: 네. 수집 목적과 항목을 정리하고, SDK 업체의 국외 이전 여부나 보관 위치도 확인해야 합니다. 계약과 법무 검토가 필요한 부분입니다. 이벤트에 실수로 입력한 음식명을 넣지 않도록 구현 리뷰 기준도 세우겠습니다.

김PM: 잠깐, 범위가 커지고 있으니까 MVP 경계를 다시 정리하죠. 앱 시작, 온보딩, 선택적 계정 생성, 홈, 음식 검색, 최근 기록, 직접 입력, 기록 수정·삭제, 주간 리포트, 알림 설정. 사진 인식, 바코드, 친구 공유, 전문가 상담은 제외. 맞습니까?

박디자이너: 거의 맞고, 즐겨찾기도 들어가야 해요. 같은 음식을 반복 입력하는 비율이 높을 거라서요. 최근 기록하고 즐겨찾기 둘 다 하면 화면이 복잡해지면 우선 최근 기록만 해도 되지만, 즐겨찾기는 별표 하나라 범위가 크진 않아요.

최개발: 즐겨찾기는 DB에 사용자 ID와 음식 ID 연결하는 테이블만 추가하면 되니까 기능 자체는 작아요. 다만 직접 입력 음식과 외부 음식 둘 다 즐겨찾기할 수 있어야 합니다.

박디자이너: 사용성 테스트라면 첫날은 진행자가 옆에서 행동을 보며 시키고, 이후에는 일주일 동안 자유 사용하게 하는 게 좋아요. 첫 기록까지 걸린 시간, 기록 중 이탈한 단계, 앱을 다시 연 횟수를 보죠. 참여자에게 너무 자세한 식단을 받지는 말고요.

최개발: 로그를 많이 남기면 개인정보가 늘어납니다. 테스트 기간에는 별도 동의를 받고, 기록 데이터는 테스트용 계정으로 분리하는 게 좋습니다. 테스트가 끝나면 데이터 삭제 방법도 안내하고요. 참여자에게 보상으로 상품권을 주면 개인정보 수집이 추가될 수 있으니 지급 처리도 확인해야 합니다.

이대표: 기록 완료율이 제일 중요합니다. 20명이 테스트하면 적어도 15명은 첫 끼니를 2분 안에 기록해야 한다는 목표를 세울까요? 검색 데이터가 부족하면 2분이 안 될 수는 있겠지만요.

최개발: 이벤트를 찍더라도 밀리초 단위 시간만 기록하고 음식 이름은 보내지 않게 하겠습니다. 앱이 백그라운드로 갔을 때 테스트 세션이 종료되는 기준도 정해야 합니다. 사용자 행동을 과도하게 추적하지 않도록 최소 데이터만 남기죠.

이대표: 리포트도 사람들이 이해하는지 봐야 합니다. 평균 칼로리나 기록한 날 기준이라는 표현이 헷갈릴 수 있으니까요. 그래프가 멋있어도 이해 못 하면 쓸모가 없습니다.

박디자이너: 처음엔 그래프를 단순하게 막대 7개로 하고, 기록 없는 날은 0으로 그리지 않고 빈칸이나 점선으로 표시해야 해요. 0칼로리처럼 보이면 안 됩니다. 목표가 없는 사용자는 목표선 없이 섭취량 추이만 보여주고요.

김PM: 주간 리포트 기간은 월요일부터 일요일로 고정할까요, 지난 7일 롤링으로 할까요?

최개발: 계산은 어느 쪽도 가능하지만 시간대 기준이 필요합니다. 사용자의 현지 시간대로 날짜를 나눌지, 서버 UTC로 자를지. 야간에 기록하면 날짜가 달라질 수 있으니 사용자 시간대를 설정에 저장하는 게 좋습니다.

이대표: 해외에서도 쓸 수는 있게 하고 싶지만, 첫 출시 타깃은 한국이에요. 한국 시간으로 기준을 잡되, 나중에 시간대 지원이 가능하도록 저장은 UTC와 현지 날짜 둘 다 고려하면 좋겠습니다.

최개발: 기록 시각은 UTC로 저장하고 사용자 시간대로 표시하는 게 기본입니다. MVP에서 시간대 변경 UI까지 만들 필요는 없고, 시스템 시간대를 읽어서 처리하겠습니다. 주간 리포트는 월요일 0시부터 일요일 23시 59분, 한국 시간 기준으로 보여주고, 주가 끝나기 전에 중간 리포트를 보여줄지는 정해야 합니다.

김PM: “지난주”라고 하면 끝난 주 기준으로 하고, 이번 주 리포트는 현재 주간 현황으로 홈에서 볼 수 있으면 되겠네요. 주간 리포트 화면은 매주 월요일부터 지난주 데이터가 보이게. 데이터가 하나도 없으면 빈 상태 안내를 넣고요.

박디자이너: 빈 상태에서 “기록이 없어요”만 보여주면 혼나는 기분일 수 있어요. “이번 주에는 아직 기록이 없어요. 한 끼부터 남겨보세요” 정도로 가볍게 쓰고, 바로 기록 추가 버튼을 넣겠습니다.

이대표: 좋네요. 목표를 달성했느냐 실패했느냐보다 기록을 이어가는 데 초점을 둡시다. 앱 카피에서 “빼먹었다”, “실패” 같은 표현은 쓰지 말고요.

최개발: 리포트 계산 로직도 주의해야 합니다. 사용자가 기록을 수정하거나 삭제하면 기존 리포트 캐시를 갱신해야 하고, 날짜 경계에서 새 리포트가 생성되는 시점을 정해야 합니다. 매번 계산하면 초기에는 문제 없지만 사용자가 늘면 서버 비용이 커질 수 있습니다.

김PM: 초기엔 사용자 요청 시 계산하고 캐시하면 되지 않나요? 규모가 작을 텐데요.

최개발: 네, MVP는 온디맨드 계산으로 가도 됩니다. 리포트 화면 진입 시 지난 7일 로그를 가져와 계산하고, 수정·삭제 후 화면을 다시 열면 갱신. 별도 배치 작업은 필요 없어 보입니다. 다만 푸시로 리포트 준비 알림을 보내려면 배치가 필요하니까 이번엔 푸시를 제외하는 판단과 맞아떨어집니다.

이대표: 좋아요. 그러면 리포트는 앱을 열었을 때 보여주고, 알림은 매일 기록 알림만. 푸시 문구도 기록을 압박하지 않게.

박디자이너: 알림 시간 선택은 오전이나 저녁만 고정하지 않고 시간 선택 휠로 할까요? 선택 폭이 넓으면 사용성이 좋지만 설정 화면이 복잡할 수 있어요.

최개발: 시스템 권한 요청이 실패하거나 거부되면 앱 안에서 알림이 켜진 것처럼 표시하면 안 됩니다. 상태를 권한 허용, 앱 내 설정, 알림 시간 이렇게 따로 관리해야 해요. 사용자가 설정 앱에서 권한을 껐다가 돌아왔을 때도 상태를 다시 읽어야 하고요.

최개발: API 계약에서 표시 의무를 확인한 뒤 UI 요구사항에 반영하겠습니다. 제공량과 출처가 비어 있는 항목은 기록할 때 기본 단위를 임의로 만들지 말고, 사용자가 참고할 수 있도록 경고를 표시해야 합니다.

김PM: 좋아요. 저도 더 이상 안건은 없고요. 30분 전반부는 여기서 끊겠습니다. 회의 끝난 다음에 제가 오늘 결정 사항을 정리해서 보내고, 미결정 사항에 담당자와 마감일을 붙일게요.

이대표: 수고하셨습니다. 하나만, 제가 말한 월 30만 원 예산은 외부 API 계약 전 검토용이지, 그 이상 쓰면 안 된다는 절대 한도는 아니에요. 품질 차이가 확실하면 추가 비용을 비교해서 다시 보고해 주세요. 자동 결제나 최소 계약 기간은 특히 확인하고요.

최개발: 네, 월 예상 비용과 호출량별 시나리오를 나눠서 가져오겠습니다. 사용자 500명, 5천 명, 5만 명 기준으로 검색 횟수를 가정하고, 캐시 적용 전후를 비교하겠습니다. 계약 해지 조건과 데이터 이용권도 확인하겠습니다.

박디자이너: 인터뷰에서는 “검색 결과가 없어도 직접 입력할 수 있다”는 흐름도 프로토타입으로 보여줄게요. 다만 공공 데이터가 실제로 얼마나 찾히는지는 인터뷰 결과와 별개로 검색 테스트 세트를 만들어야 합니다.

김PM: 제가 검색 테스트 메뉴 50개를 오늘 중 초안으로 만들고, 이대표님이 브랜드 메뉴 후보를 추가해주시면 금요일에 같이 확인하겠습니다. 끝으로 한 번 더, 지금 당장 고정한 건 사진 인식 제외, 결제 제외, 기본 기록과 주간 리포트 무료, 알림은 선택형 하루 한 번. 로그인 방식하고 식품 API는 이번 주 확정. 맞죠?

이대표: 네. 그중에서도 외부 서비스에 기록 데이터를 보내지 않는 게 중요합니다. 앱 분석 이벤트도 음식 이름이나 칼로리를 보내지 않는 걸로 지켜주세요.

최개발: 그렇게 하겠습니다. API 요청 검토와 코드 리뷰 체크리스트에 개인정보 항목을 넣을게요. 검색어도 외부 업체 처리 조건을 확인하고, 사용자 식별자는 붙이지 않겠습니다.

박디자이너: 저는 첫 화면을 기록 중심으로 잡고 칼로리 숫자는 보조로 내려서 와이어프레임 공유하겠습니다. 목표를 설정하지 않은 사람도 자연스럽게 쓸 수 있도록 빈 상태하고 안내 문구까지 같이 준비할게요.

김PM: 좋아요. 그럼 전반부 회의 여기까지 하겠습니다. 각자 이번 주 액션은 제가 문서로 정리해서 오후에 공유할게요. 녹음은 여기서 멈출게요.
김PM: 그러면 앞에서 사용자 문제랑 타깃 얘기한 데 이어서, 지금부터는 실제로 8주 안에 어디까지 만들 수 있나를 맞춰볼게요. 지금 시간 기준으로 회의 후반부고요. 오늘 결정이 필요한 건 MVP 범위, 화면, 데이터 구조, 외부 API, 일정, 요금, 개인정보, 리포트랑 푸시, 테스트 계획까지입니다. 다 한 번에 완벽하게 결론 내기보다는, 결정할 것과 확인할 것을 나눠서 적겠습니다.

이대표: 네. 다만 MVP라고 해놓고 나중에 꼭 필요한 게 빠지면 안 되니까, 출시하고 나서 사용자한테 “이건 다음 버전입니다”만 계속 말하는 상황은 피하고 싶어요. 최소한 기록하고, 확인하고, 일주일 뒤에 내가 어떻게 먹었는지 돌아볼 수는 있어야 합니다.

박디자이너: 동의해요. 그럼 일단 사용자 흐름을 하나로 잡아볼게요. 가입하고, 목표를 정하고, 오늘 먹은 걸 기록하고, 하루나 주간 리포트를 보는 흐름. 이 흐름에 필요 없는 기능은 우선순위를 낮추고요. 그런데 음식 기록을 사진으로 할지 검색으로 할지, 둘 다 할지가 화면 수랑 개발 범위를 꽤 크게 바꿔요.

최개발: 둘 다 넣는 건 가능한데, 사진에서 음식 이름이나 칼로리를 자동으로 뽑는 데까지 MVP에 넣으면 이야기가 달라집니다. 카메라로 사진을 찍어서 저장만 하는 것과, 사진을 분석해서 음식 항목으로 만드는 건 완전히 다른 작업이에요. 모델 호출, 결과 보정, 실패했을 때의 편집까지 있어야 합니다.

이대표: 사진 분석은 요즘 사용자들이 당연히 기대하지 않나요? 식단 앱이라고 하면 찍으면 알아서 되는 걸 떠올릴 것 같은데요.

최개발: 기대는 하죠. 그런데 사진 한 장에서 김치찌개랑 밥이 같이 보였을 때 각각의 양까지 정확하게 추정하는 건 어렵습니다. 사진 분석 결과가 “밥 210그램, 김치찌개 280그램”이라고 나왔는데 실제로 밥을 반만 먹었으면 기록이 틀려요. 자동이라고 홍보했다가 계속 고쳐야 하면 오히려 불만이 생깁니다.

박디자이너: 그러면 사진은 첨부하고, 기록은 검색이나 직접 입력으로 하게 하는 방식은요? 사진만 올리면 식단 기록이 된다고 착각하지 않도록 “사진은 보조 기록”이라고 명확히 쓰고요.

이대표: 사진 보조는 좀 약해 보이는데. 그러면 우리 앱만의 차별점이 뭔가요? 검색해서 먹은 거 넣는 건 기존 앱도 다 하잖아요.

김PM: 차별점은 오늘 하나의 숫자를 맞히는 것보다, 반복적으로 기록하기 쉬운 데 두면 어떨까요. 음식 이름 검색, 자주 먹는 메뉴, 지난 기록에서 복사, 간편한 양 조절. 그리고 주간 리포트에서 “평일 점심 단백질이 낮은 편” 같은 식으로 행동을 이해하기 쉽게 알려주는 거요. 사진 분석은 범위에 넣더라도 1차는 실험 기능으로 제한하고 정확도를 검증하는 게 안전해 보여요.

최개발: 사진 분석을 넣으려면 외부 API 비용도 봐야 합니다. 요청당 과금이면 사용자 수가 늘어날수록 예상 비용이 생겨요. 음식 분류가 되는 API가 있어도 한국 음식 인식률은 별도로 테스트해야 하고요. API 응답에서 칼로리나 영양 정보까지 가져오는지, 음식 라벨만 주는지에 따라 우리가 붙여야 하는 데이터도 달라집니다.

이대표: 그럼 MVP에서 카메라는 빼는 건가요?

박디자이너: 저는 카메라 자체를 빼는 건 반대예요. 입력이 안 되더라도 기록할 때 사진을 저장하는 기능은 꽤 쓸모가 있을 것 같아요. 외식 메뉴 이름을 모를 때 사진만 남겨도 나중에 기억할 수 있으니까요. 다만 사진으로 칼로리를 자동 계산해준다고 말하지는 않는 거죠.

김PM: 이건 두 단계로 나누죠. MVP에는 사진 첨부와 식사 사진 보기까지 포함. 자동 인식은 8주 일정 내 필수 범위로 잡지 않고, 기술 검증 결과가 괜찮으면 뒤에 별도 기능 플래그로 넣습니다. 사진 분석이 안 되더라도 핵심 흐름이 완성되는 구조로요.

최개발: 그 정도면 가능해요. 사진은 원본을 앱 서버에 직접 올릴지, 스토리지에 올리고 DB에는 경로만 보관할지 결정해야 해요. DB에 이미지 자체를 넣으면 안 됩니다. 오브젝트 스토리지에 저장하고 식사 기록 테이블에는 파일 키하고 썸네일 키 정도만 두는 게 맞습니다.

박디자이너: 화면 얘기 먼저 해볼게요. 저는 첫 실행에서 성별, 나이, 키, 몸무게, 목표를 한 화면에 다 받는 방식은 피하고 싶어요. 가입 직후에 질문이 많으면 이탈하거든요. 최소 입력으로 시작한 다음 목표 설정으로 넘어가는 식이 나을 것 같아요.

이대표: 키나 몸무게를 안 받고도 칼로리 목표를 어떻게 계산하죠?

박디자이너: 선택적으로 입력하게 하면 돼요. 몸무게 감량이 목표면 체중과 목표 체중을 받을 수 있고, 그냥 식사 패턴을 보고 싶은 사람은 “목표 없이 기록만 하기”를 선택하게요. 앱이 체중을 입력하지 않으면 못 쓰는 구조가 되면 안 될 것 같습니다. 민감한 정보를 안 내고 싶은 사람도 있으니까요.

최개발: 계산 기준도 그럼 두 가지가 되네요. 프로필 정보가 충분하면 권장량을 계산하고, 부족하면 사용자가 직접 목표를 설정하거나 목표 없이 사용. 여기서 계산값을 의학적 처방처럼 보이게 하면 안 됩니다. 화면에 추정치라고 표시해야 하고, 특히 임신·수유나 질환 같은 상황은 별도로 다룰 건지 정해야 합니다.

김PM: MVP에서 질환 관련 추천은 안 하는 걸로 합시다. 사용자에게 의료 조언을 제공하는 앱이 아니고, 음식 기록과 일반적인 영양 정보 서비스라고 정리할게요. 목표 칼로리도 “참고 목표”라고 쓰고요. 기저질환이나 특수 상황에 대해서는 전문가와 상담하라는 안내를 설정 화면이나 목표 화면에 넣을 수 있겠습니다.

이대표: 목표 없이 쓰는 건 괜찮아요. 대신 가입은 해야 하나요? 익명으로 바로 써보고 마음에 들면 계정 만들게 하는 게 낫지 않나?

최개발: 익명 시작도 구현은 됩니다. 다만 기록을 기기 안에만 두면 기기 바꿀 때 데이터가 사라져요. 익명 계정을 서버에서 만들어서 나중에 이메일이나 소셜 계정에 연결하는 방법도 있고, 아예 처음부터 가입을 받는 방법도 있죠. 계정 전환과 데이터 연결 처리를 해야 해서 익명 시작이 공짜 기능은 아닙니다.

박디자이너: 우선 게스트로 오늘 한 끼만 기록해보게 하면 부담이 낮아지긴 해요. 근데 온보딩까지 하고 나서 로그인 팝업이 갑자기 뜨면 끊길 수도 있어요. 첫 실행에서 “계정 없이 시작”을 눈에 띄게 두고, 백업이나 다른 기기에서 보기 전에 계정 연결을 권하는 건 어때요?

김PM: 일정 때문에 그게 얼마나 더 들어가는지 확인이 필요하겠네요.

최개발: 게스트 데이터를 나중에 회원 계정으로 병합하는 것까지 하면 백엔드랑 QA 시간이 늘어납니다. 이번에는 애플, 구글, 이메일 중 하나 이상으로 먼저 로그인하는 게 단순합니다. 모바일은 애플과 구글 로그인이 기본이고, 이메일 링크 로그인도 넣을 수 있어요. 그런데 세 가지를 다 하려면 심사와 인증 설정이 각각 필요해요.

이대표: 소셜은 있어야 할 것 같은데, 이메일이랑 애플, 구글 전부요. 국내 사용자 기준으로 카카오도 빼기 어렵지 않나요?

최개발: 카카오까지 넣으면 4개예요. 구현 자체보다 운영에서 계정 연결, 탈퇴, 로그인 실패 대응을 각 제공자별로 해야 합니다. 8주 안에 모바일 iOS, 안드로이드 둘 다 나가야 하는데, 인증 제공자 네 개는 MVP에서 우선순위를 낮추는 게 낫습니다.

김PM: 1차는 애플과 구글, 이메일 중에서 어떤 조합이 현실적이에요?

최개발: 이메일 로그인하고 애플, 구글 중 두 개까지요. 플랫폼별 심사 조건을 고려하면 iOS는 애플 로그인을 넣고, 안드로이드는 구글을 넣는 방식이 자연스럽긴 한데, 공통 계정으로 이메일을 같이 제공하는 편이 계정 복구는 편합니다. 대신 카카오는 1차에서 제외하고 사용 반응을 보죠.

이대표: 카카오를 뺄 때 가입 전환율은 체크해야겠네요. 사용자 조사에서는 카카오가 편하다는 얘기도 나왔어요.

김PM: 그럼 확인 항목으로 남기고, 지금은 구현 우선순위를 애플·구글·이메일로 잡겠습니다. 로그인 화면은 셋을 다 넣되, 이번 주 안에 최개발님이 SDK랑 심사 관련 일정 다시 확인해서 위험하면 하나를 줄이는 걸로요.

박디자이너: 화면 목록을 읽어볼게요. 첫째 가입·로그인. 둘째 온보딩과 목표 설정. 셋째 오늘 홈. 넷째 음식 검색과 결과 선택. 다섯째 식사 기록 상세, 양과 끼니 선택. 여섯째 기록 확인과 편집. 일곱째 주간 리포트. 여덟째 기록 캘린더나 날짜별 조회. 아홉째 설정, 개인정보, 알림 설정. 열 개 정도네요.

이대표: 네, 친구랑 경쟁하는 건 지금은 범위 밖이라고 봅니다. 초기에 사람들끼리 공유할 기능보다 개인이 꾸준히 쓰게 하는 게 중요해요. 다만 가족이나 트레이너에게 공유하고 싶다는 요청은 나중에 나올 수 있겠죠.

김PM: 공유는 2차 검토로 남기고 MVP는 개인 기록으로 제한하겠습니다. 홈에서 제일 먼저 보여줄 건 뭐죠? 칼로리 잔여량, 끼니 기록 버튼, 오늘 먹은 목록 중에요.

박디자이너: 저는 “기록하기” 버튼이 먼저 보여야 한다고 생각해요. 칼로리 숫자를 가장 크게 두면 목표량을 채우지 못한 날에 죄책감을 줄 수 있어요. 상단에는 오늘 날짜, 오늘 기록 상태, 끼니별 기록을 두고, 칼로리와 주요 영양소는 한 단계 아래에서 확인하게 하고 싶어요.

이대표: 그런데 숫자를 안 보여주면 식단 앱이라는 느낌이 약할 수도 있잖아요.

박디자이너: 안 보여주는 게 아니라 강조 순서를 조정하는 거예요. 예를 들어 “현재 기록된 섭취량 1,240kcal”라고 보여주고, 목표까지 남은 양은 보조로 두는 거죠. 사용자가 목표를 설정하지 않았으면 잔여량을 숨기고 실제 기록된 값만 보여주고요. 숫자 하나로 평가하는 느낌은 줄일 수 있어요.

최개발: 칼로리를 보여주려면 음식 DB 데이터의 신뢰도 문제가 있습니다. 검색해서 선택한 음식에 영양 정보가 없으면 0으로 처리하면 안 돼요. 값이 없다는 상태와 실제 영양소가 0인 상태를 구분해야 합니다. 화면에 “영양 정보 없음”으로 나올 수 있게 API 응답 구조도 잡아야 하고요.

김PM: 기록 단위는 어떻게 잡을까요? 음식 이름만 저장할지, g 단위까지 필수로 받을지.

박디자이너: 기본 제공량을 먼저 보여주고, 사용자가 필요하면 양을 조절하게 하고 싶어요. 예를 들어 사과 한 개, 밥 한 공기, 달걀 한 개처럼요. 처음부터 100g 기준 숫자를 강요하면 입력이 번거롭습니다. 직접 무게를 넣는 사람은 상세 편집으로 들어가게 하고요.

최개발: 그러려면 음식 데이터에 제공량 이름과 기준 g이 있어야 합니다. 영양정보가 100g 기준이면 선택한 제공량으로 환산할 수 있어요. API에서 “1회 제공량”이 제각각으로 내려오면 단위 통일을 해야 하니까, 화면에서 단위를 표시하는 규칙은 정해줘야 합니다. ml, g, 개, 컵, 인분을 전부 지원하면 테스트 케이스가 늘어요.

이대표: 사용자가 컵라면 반 개를 먹을 수도 있잖아요. 양 조절은 0.5도 돼야죠.

최개발: 수량은 소수점 허용하면 되고요. 다만 단위가 “개”인 음식은 0.5개가 자연스럽지만 “한 그릇”은 0.5그릇이 애매할 수 있어요. 그래도 숫자 입력으로는 허용하고, 표시를 반 그릇으로 자동 바꾸는 건 1차에서 안 해도 됩니다.

박디자이너: 검색 결과에서 음식 이름, 브랜드나 종류, 기준량, 칼로리를 같이 보여주고, 선택하면 양 조절 화면으로 넘어가요. 브랜드 제품이랑 일반 음식이 섞일 수 있으니 “브랜드” 라벨을 붙일게요. 결과가 너무 많으면 최근 검색과 자주 먹는 음식이 위에 먼저 보였으면 좋겠어요.

최개발: 최근 기록은 사용자별로 저장하면 되고, 자주 먹는 음식은 최근 30일에 몇 번 기록했는지 계산하면 됩니다. 실시간으로 매번 집계하지 않아도 돼요. MVP에는 최근 검색과 최근 기록에서 복사하기를 먼저 넣고, 빈도 기반 추천은 구현 여유가 있으면 추가하는 게 낫겠습니다.

김PM: 외부 음식 DB API는 어떤 후보가 있죠? 지난번에 얘기한 데이터 공급처 두 곳이 있었는데요.

최개발: 하나는 국제 식품 데이터가 많고 무료 구간이 있지만 한국 음식 이름과 브랜드 제품 커버리지가 부족해요. 다른 곳은 국내 음식 데이터가 상대적으로 낫지만 월간 호출량 기준으로 유료 계약이 필요합니다. 정확한 응답 속도와 상업적 이용 범위는 아직 계약서 확인 중이고요. 라이선스가 앱 화면에 영양 정보를 재표시해도 되는지, 캐시를 며칠 보관할 수 있는지 확인해야 해요.

이대표: 무료 API로 먼저 붙이고 나중에 바꾸면 안 돼요?

최개발: 가능은 하지만, 음식 식별자 구조가 서로 다르면 데이터 이관 비용이 생깁니다. API 응답을 그대로 앱까지 전달하지 말고 우리 쪽 표준 모델로 변환해야 해요. 예를 들면 내부 음식 ID, 외부 공급자 ID, 표시 이름, 브랜드, 영양 정보, 단위, 출처를 따로 저장하는 방식입니다. 공급자를 바꾸더라도 앱 화면은 내부 모델만 보게 해야 합니다.

김PM: 그럼 API 연결부는 공급자 어댑터 구조로 만들고, 1차 공급처는 계약 확인 후 선정하는 걸로 합시다. 검색 응답은 내부 표준형으로 정규화. 호출 실패하면 기록 기능 전체가 막히지 않도록 최근 음식과 직접 입력은 가능해야 합니다.

박디자이너: 직접 입력은 어떤 수준으로요? 음식 이름만 입력하게 할지, 칼로리도 입력하게 할지.

이대표: 이름만 넣으면 영양 정보가 없어서 리포트가 의미 없어질 수 있잖아요.

박디자이너: 그래도 검색에 없는 메뉴를 기록하려는 사용자는 많을 거예요. 이름만이라도 저장해야 합니다. 칼로리와 탄단지 입력은 선택으로 넣고요. 모르겠으면 비워둘 수 있게 해야 해요.

최개발: 그러면 사용자 입력 음식은 별도 테이블에 두거나 공통 음식 테이블에 source_type을 둬야 합니다. 공통 음식 데이터와 사용자 개인 음식 데이터는 노출 범위를 분리해야 하고요. 개인 음식 이름을 다른 사용자 검색 결과에 공개하지 않는 걸 기본으로 하죠. 나중에 공용 DB에 올리려면 동의를 별도로 받아야 합니다.

김PM: 개인 음식 정보는 비공개 기본값으로. 그리고 리포트 계산은 영양 값이 없는 기록을 제외하되, 제외된 음식이 있다고 알 수 있게 해야 할까요?

박디자이너: “일부 기록에 영양 정보가 없어 합계에 포함되지 않았어요” 정도면 될 것 같아요. 사용자한테 기록 자체가 사라진 것처럼 보이면 안 돼요.

이대표: 데이터베이스 구조를 구체적으로 설명해 주세요. 제가 기술 용어는 잘 몰라서, 나중에 사용자 기록이 쌓이면 우리가 뭘 갖게 되는지 알고 싶어요.

최개발: 큰 덩어리로 말씀드리면 사용자, 사용자 프로필, 목표, 음식, 식사 기록, 식사 기록에 포함된 음식 항목, 알림 설정, 리포트 집계, 동의 및 삭제 요청 정도입니다. 사용자 한 명이 하루에 여러 식사를 만들고, 각 식사 안에 음식 항목이 여러 개 들어가는 구조예요. 아침 기록 하나에 밥, 계란, 김치가 들어가면 식사 테이블 한 건, 음식 항목 테이블 세 건이 됩니다.

이대표: 그럼 날짜별로 식사가 묶이고, 음식 데이터는 따로 있는 거네요.

최개발: 맞습니다. 식사에는 날짜, 시간대, 식사 타입, 메모, 사진 경로가 있고, 음식 항목에는 음식 ID, 사용자가 선택한 이름 스냅샷, 양, 단위, 환산된 영양값이 들어갑니다. 이름 스냅샷을 저장하는 이유는 외부 음식 DB의 이름이나 값이 나중에 바뀌어도 과거 기록이 갑자기 달라지지 않게 하기 위해서예요.

김PM: 영양값도 기록 시점에 복사해두는 거죠?

최개발: 네. 당시 사용자가 기록한 값은 고정하고, 외부 DB의 최신 정보는 별도 음식 마스터에 저장합니다. 그래야 공급처가 값 수정해도 기존 기록의 리포트가 조용히 바뀌지 않아요. 사용자가 직접 “최신 음식 정보로 업데이트”를 누르는 기능은 이번에 필요 없고요.

박디자이너: 날짜 기준은 사용자 시간대로 저장하나요? 출장 가거나 해외에 가면 날짜가 바뀌잖아요.

최개발: DB에는 UTC 시각으로 저장하고, 사용자 프로필에 시간대를 보관해서 화면에 날짜를 표시하는 게 기본이에요. 다만 식사 날짜는 기록 생성 시점의 로컬 날짜도 함께 저장할 수 있습니다. 새벽 두 시에 야식을 먹었을 때 전날로 볼지 당일로 볼지도 정해야 해요.

이대표: 사람마다 다르게 생각할 텐데요. 밤 11시 50분에 먹기 시작해서 자정 넘겨 기록할 수도 있고요.

박디자이너: 기본값은 기록을 저장한 날짜로 하고, 날짜 선택을 직접 바꿀 수 있게 하면 어떨까요. 식사 시간은 선택 사항으로 두고요. 새벽 식사 자동으로 전날에 붙이는 규칙을 만들면 예외가 너무 많아질 것 같아요.

김PM: 동의해요. 저장 시점의 현지 날짜를 기본으로 하고, 기록 편집에서 날짜와 시간을 바꿀 수 있게. 사용자 시간대 바뀌면 과거 기록 날짜를 자동 재계산하는 건 하지 않는 걸로요.

최개발: 그럼 프로필에 타임존, 언어, 단위 설정을 갖고, 식사에는 로컬 날짜 키와 기록 시각을 함께 저장하겠습니다. 몸무게 기록을 매일 받는 건 이번 범위에 넣을까요?

이대표: 앞에서 체중 감량 목표 얘기했으니까 체중 추이는 있으면 좋을 것 같은데요. 앱 이름이 식단 기록이니까 너무 확장하지 않는 게 좋겠다는 생각도 있고요.

박디자이너: 몸무게는 온보딩에서 한 번 선택적으로 받고, 매일 기록은 2차로 넘기는 게 좋을 것 같아요. 홈에 체중 그래프까지 넣으면 화면 구조가 또 커져요. MVP에서는 목표 계산에 쓴 값을 프로필에서 수정하는 정도로요.

김PM: 체중 일별 추적은 제외. 입력한 키와 몸무게, 생년월일은 목표 계산과 표시를 위해 수집하는데, 수집 이유를 분명히 설명하고 언제든 수정·삭제 가능하게 하겠습니다. 성별은 계산에 필요한 경우에도 선택으로 받을지, 선택하지 않았을 때 계산을 어떻게 할지 확인해야 해요.

최개발: 프로필 정보는 서비스 DB에 저장하고, 인증 토큰이나 비밀번호는 우리가 직접 들고 있지 않는 구조로 할 수 있어요. 이메일 로그인은 해시 처리나 인증 제공자를 통해 관리하고, 원문 비밀번호를 저장하지 않습니다. 민감한 프로필 정보 접근 권한은 서버에서 제한하고 로그에 값이 찍히지 않게 해야 해요.

이대표: 로그에 개인정보가 남는다는 건 어떤 경우예요?

최개발: 오류가 났을 때 요청 전체를 그대로 로그로 남기면, 음식 메모나 체중 같은 값이 로그 서비스에 복사될 수 있습니다. 그래서 사용자 ID는 내부 익명 ID로 남기고, 요청 본문은 기록하지 않거나 필요한 필드만 마스킹해야 해요. 분석 이벤트에도 음식 이름이나 자유 입력 메모를 그대로 보내지 않는 게 좋습니다.

김PM: 그럼 분석 도구에는 “식사 기록 완료”, “검색 실행”, “리포트 열람” 같은 이벤트만 보내고 실제 음식명이나 몸무게는 포함하지 않습니다. 개인정보 처리방침 초안은 법무 검토가 필요하겠네요.

이대표: 네. 그리고 데이터를 국내에 저장해야 하는지, 해외 클라우드 써도 되는지 확인해야 해요. 외부 API로 음식 정보 검색할 때 사용자 정보를 보내나요?

최개발: 음식 검색어는 외부 API로 넘어갈 수 있어요. 예를 들어 “떡볶이”를 검색하면 검색어 자체가 공급자에 전달됩니다. 사용자 이메일이나 프로필 ID는 보내지 않게 프록시 서버를 두고요. 다만 검색어 자체도 사용자가 직접 입력한 데이터라 개인정보는 아니더라도 사용 패턴 정보가 될 수 있습니다. 공급자 계약의 데이터 보관 정책을 확인해야 합니다.

박디자이너: 자유 입력 검색창에서 사용자가 이름이나 장소를 넣을 수도 있으니까, 검색어가 외부로 간다는 걸 약관 어디에 써야 할지 봐야겠네요. 앱 화면에 매번 경고창을 띄우는 건 너무 과해요.

김PM: 동의 문구와 개인정보 처리방침에 외부 처리 위탁 내용을 명시하고, 계약 가능한 API로 제한하겠습니다. 사진은 외부 분석 API에 전달하지 않는 걸로 1차에서는 정하면 이슈가 하나 줄어요.

최개발: 네, 사진 저장은 우리 스토리지에만 하고, 공유 링크는 공개 URL이 아니라 만료되거나 인증이 필요한 방식이어야 합니다. 이미지 파일 메타데이터에 위치 정보가 들어갈 수 있어서 업로드 전에 EXIF 제거도 검토해야 해요. 사진 권한을 앱에서 요청할 때 전체 사진 접근 대신 선택한 사진만 접근하도록 하겠습니다.

이대표: 사용자가 탈퇴하면 사진하고 기록은 바로 다 지워져야 하나요?

최개발: 사용자 관점에서는 탈퇴 요청 후 일정 기간 내 삭제한다고 명확히 안내해야 합니다. 시스템 백업은 즉시 물리적으로 지우기 어려울 수 있으니 백업 보존 기간과 삭제 처리 정책을 정해야 하고요. 법적으로 보관해야 하는 자료가 있는지 회계나 결제 기능을 붙일 때 따로 확인해야 합니다. 현재 MVP에 결제가 없으면 결제 내역은 없겠지만, 계정 삭제와 기록 삭제는 분리해서 선택할지도 논의해야 해요.

김PM: 탈퇴하면 계정과 식사 기록을 모두 삭제하는 게 기본이죠. 데이터 내보내기까지 MVP에 넣으면 일정이 늘 수 있는데, 최소한 사용자가 앱 안에서 계정 삭제를 요청할 수 있어야 합니다. 고객센터에 메일만 보내라는 방식은 피하고요.

박디자이너: 설정에 “계정 삭제” 버튼을 두되, 실수 방지를 위해 재인증하고 삭제되는 데이터를 안내한 뒤 확인하게 할게요. 탈퇴 전에 CSV로 내보내기 같은 건 이번에는 빼도 되는지 확인해 주세요. 특히 사용자가 기록을 쌓은 뒤 빠져나갈 권리가 있는 부분은 법무 검토가 필요합니다.

최개발: 계정 삭제 요청을 받으면 상태를 삭제 대기 중으로 바꾸고, 앱 로그인과 푸시 토큰을 먼저 비활성화한 다음 비동기로 사진과 기록을 지울 수 있습니다. 요청 시각을 남기되 삭제된 사용자와 연결할 수 없는 형태로 보존할지, 운영 로그를 어느 기간 유지할지도 개인정보 담당과 정해야 합니다.

이대표: 알겠습니다. 요금 얘기도 해보죠. 무료로 시작하고 나중에 프리미엄 구독을 넣나요? 아니면 처음부터 월 구독을 받을까요?

김PM: 저는 MVP는 무료로 출시하고, 이용 패턴을 보고 과금 가설을 세우는 게 낫다고 봅니다. 유료화가 들어가면 스토어 결제, 영수증 검증, 해지·환불, 가격 실험까지 일정이 크게 늘어요. 지금은 기록 지속률을 확인하는 게 우선입니다.

이대표: 무료만으로 사용자 확보가 될까요? 음식 DB API 비용도 있고 이미지 저장 비용도 있어요.

최개발: 무료 API의 쿼터를 넘길 수 있으니 월간 사용자 수와 검색 횟수별로 비용을 계산해야 합니다. 사진 용량은 업로드 때 최대 크기 제한을 두고 썸네일을 만들면 줄일 수 있어요. 예를 들어 원본 8MB까지 무제한으로 받는 식은 곤란하고, 앱에서 긴 변을 1,600픽셀 정도로 줄여 압축하는 정책을 둘 수 있습니다. 저장 기간과 사용량도 모니터링해야 해요.

박디자이너: 사용자한테는 “사진 용량 초과”를 친절하게 알려주고, 업로드 중 취소나 재시도도 가능해야겠네요. 네트워크가 끊겼을 때 기록 저장이 실패했는데 완료된 줄 알고 앱을 닫는 경우가 제일 걱정돼요.

최개발: 오프라인 저장은 MVP에 넣을지 결정해야 합니다. 완전한 오프라인 동기화는 충돌 처리가 복잡해요. 우선 임시 저장을 로컬에 하고 네트워크가 복구되면 재전송하는 정도는 가능합니다. 다만 같은 기록을 두 번 보내지 않도록 요청 ID가 있어야 합니다.

김PM: 식사 기록 중 네트워크가 끊기는 경우를 고려하면 기본 입력은 로컬에 임시 저장하고, 서버 저장 성공 여부를 표시하는 걸 포함하는 게 좋겠네요. 오프라인 상태에서 음식 검색을 새로 하는 건 못 하더라도 최근 음식은 보여줄 수 있고요. 사진 업로드는 온라인일 때만 진행한다고 명확히 안내하면 되겠습니다.

이대표: 요금제는 그럼 출시 시점에는 무료, 프리미엄은 로드맵에만 올리죠. 유료 기능 후보는 뭘로 봐야 하나요?

박디자이너: 월간 상세 리포트, 고급 목표 설정, 데이터 내보내기, 여러 기기 동기화 같은 게 후보일 수는 있는데, 개인정보 접근을 유료로 막는 느낌은 안 나야 해요. 기본적인 기록 열람이나 계정 삭제는 당연히 무료여야죠.

최개발: 동기화는 유료로 막으면 사용자 데이터 손실 문제와 연결돼서 조심해야 합니다. 클라우드에 저장하고 여러 기기에서 보는 건 기본 기능으로 보는 게 사용자 신뢰에는 더 좋습니다. 프리미엄을 한다면 분석의 깊이나 콘텐츠, 개인화 서비스 쪽이 낫습니다.

이대표: 코치가 추천해주는 기능은요? 예를 들어 단백질이 부족하다고 알려주고 식품을 추천하는 식으로.

김PM: 그건 2차 이후에 데이터 품질하고 추천 책임을 확인한 다음이 좋겠습니다. MVP 리포트는 사실에 가까운 관찰만 하죠. “이번 주 기록 중 점심 평균 단백질이 아침보다 낮았습니다” 같은 문장. “내일 닭가슴살을 드세요”처럼 직접 권하는 건 피하고요.

박디자이너: 주간 리포트 화면에서 가장 중요한 건 사용자에게 판단을 강요하지 않는 문장이라고 생각해요. “목표 달성 실패” 대신 “기록된 5일 중 3일은 설정한 목표 범위 안에 있었어요” 식으로요. 아예 기록을 안 한 날을 섭취 0으로 계산하면 안 되고, 기록이 없다는 걸 별도로 표시해야 합니다.

최개발: 맞아요. 기록이 없는 날과 음식 영양정보가 없어서 합계가 불완전한 날을 구분해야 합니다. 최소 기록 기준도 필요합니다. 아침만 기록한 날을 하루 전체로 볼지, 리포트에서 “부분 기록”으로 볼지요.

이대표: 사용자가 먹은 걸 전부 안 적었는지 우리가 알 수는 없죠. 그러니 기록된 내용 기준이라고 계속 표시해야겠네요.

김PM: 맞습니다. 화면 문구는 “기록된 식사 기준”을 반복해서 명시하고, 주간 리포트에서 기록한 날짜 수와 미기록 날짜 수를 같이 보여줍시다. 하루 총량을 확정적인 실제 섭취량으로 표현하지 않고 “기록된 섭취량”이라고 하겠습니다.

박디자이너: 주간 리포트 구성은 일단 세 부분을 생각했어요. 기록 지속성, 평균 에너지와 탄단지, 끼니별 패턴. 첫 카드에는 “이번 주 7일 중 5일 기록”처럼 보여주고, 두 번째는 기록이 있는 날만 평균을 계산하고, 세 번째는 아침·점심·저녁 중 어디에 기록이 몰렸는지 보는 거예요.

이대표: 식이섬유나 나트륨은 넣을 수 없나요? 건강 관심 있는 사람은 그걸 많이 볼 것 같은데요.

최개발: 음식 DB에 데이터가 충분히 있어야 표시할 수 있어요. 나트륨은 일부 제품에서 괜찮지만 일반 식당 음식은 빈 값이 많을 수 있습니다. 영양소를 많이 늘릴수록 데이터 불완전이 눈에 띄어요. MVP는 칼로리, 단백질, 탄수화물, 지방으로 하고, 식이섬유나 나트륨은 커버리지를 확인한 다음 넣는 게 낫습니다.

박디자이너: 그럼 화면에 네 가지를 다 같은 비중으로 보여주지 않고, 칼로리와 탄단지 중심으로요. 데이터가 부족한 영양소는 카드 자체를 숨길 수 있게 디자인 시스템에서 유연하게 해둘게요.

김PM: 주간 비교도 있어야 하나요? 이번 주와 지난주를 비교하는 그래프요.

이대표: 있으면 좋아요. 사용자에게 변화가 보여야 계속 쓸 것 같아요.

최개발: 주별 비교는 가능한데, 기록한 날 수가 다를 때 단순 총합을 비교하면 오해가 생겨요. 지난주는 7일 기록했고 이번 주는 이틀만 기록했는데 섭취량 총합만 보면 이번 주가 낮다고 나와요. 일별 평균으로 비교하고 기록 일수를 함께 보여줘야 합니다. 그리고 표본이 2일밖에 없는데 “감소했다”고 확정적으로 말하면 안 됩니다.

박디자이너: 비교 문장은 기록일이 4일 이상일 때만 보여주는 식으로 할까요? 아니면 그래프는 보여주고 “기록이 적어 비교하기 어려워요”라고 안내할까요.

김PM: 4일 기준을 정하는 근거가 있어야 합니다. MVP에서는 지난주와의 수치 비교보다 이번 주 현황에 집중하고, 기록 일수가 충분한 경우에만 비교 카드가 나오게 하죠. 최소 기준은 분석가나 영양 전문가에게 검토받을 수 있으면 좋겠는데, 일정상 외부 검토까지 8주 안에 가능할까요?

이대표: 전문가 자문을 1시간 정도라도 받을 수 있도록 제가 연결해볼게요. 수치 추천까지는 안 하더라도 문구가 오해를 부르지 않는지 봐달라고요.

최개발: 리포트를 매일 계산해서 저장할지, 화면을 열 때 집계할지도 결정해야 합니다. 데이터가 초기에는 적으니 요청 시 계산해도 괜찮고, 주간 리포트 캐시를 하루 한 번 생성하는 방법도 있어요.

최개발: MVP에서 사용자가 일주일치 기록을 보려고 들어왔을 때 SQL 집계를 해도 규모상 부담은 거의 없습니다. 다만 외부 API를 호출해서 화면을 만들면 안 됩니다. 영양 정보는 기록 시점에 저장하고, 리포트는 우리 DB 기준으로 계산해야 합니다. 나중에 사용자 수가 늘면 캐시를 붙이면 돼요.

김PM: 리포트는 사용자가 열 때 서버에서 계산, 성능 측정 후 캐시 검토. 푸시는 그 리포트를 알려주는 용도인가요, 기록을 잊지 않게 하는 용도인가요?

박디자이너: 둘 다 가능하지만 한 번에 여러 알림을 켜면 부담스러워요. 가입하자마자 푸시 허용 팝업을 띄우기보다는 기록을 한두 번 한 뒤에 “원하는 시간에 알림을 받을까요?”라고 물어보는 게 낫습니다. 사용자가 시간을 직접 정하게 하고요.

이대표: 알림은 매일 한 번 정도면 괜찮지 않을까요? 식사 기록 앱이면 저녁에 기록하라고 알려줘야죠.

김PM: 저녁 알림이 모든 사람에게 맞지는 않을 것 같아요. 교대 근무자도 있고, 저녁 식사를 안 하는 사람도 있고요. 기본값을 정하더라도 선택할 수 있어야 합니다. 아침, 점심, 저녁 중에 원하는 시간 하나를 고르게 할까요?

최개발: 푸시는 iOS와 안드로이드 모두 권한이 필요하고, 토큰 갱신과 무효화 처리가 있어야 합니다. 서버에서 사용자 시간대에 맞춰 예약 푸시를 보내려면 스케줄러가 필요하고요. 하루 종일 켜져 있는 서비스가 아니어도 클라우드 작업으로 예약할 수 있지만, 중복 발송 방지와 실패 재시도가 필요합니다.

박디자이너: 사용자 입장에서는 시간 선택이 15분 단위까지 있으면 복잡해요. 30분 간격 정도면 충분할 것 같아요. 그리고 “오늘 식단을 기록해보세요”라는 문구도 압박처럼 느껴질 수 있으니 “오늘 먹은 것을 가볍게 정리해볼까요?” 같은 톤으로요.

이대표: 매일 기록을 안 한 사람한테는 푸시를 더 보내야 재방문하지 않나요?

김PM: 과한 푸시는 앱 삭제로 이어질 수도 있어요. MVP에서는 사용자가 설정한 시간에 하루 최대 한 번, 주간 리포트는 별도 선택으로 한 번 정도로 제한합시다. 기록을 완료한 날에는 저녁 알림을 자동으로 건너뛰는 규칙이 필요하고요.

최개발: 가능합니다. 다만 하루 기록 여부를 어디까지 봐야 하는지 정해야 해요. 식사 하나만 기록하면 그날 기록 완료로 처리할지, 사용자가 정한 목표 끼니를 기준으로 할지요. 단순하게 그날 식사 기록이 한 건 이상 있으면 리마인더를 보내지 않는 걸로 하면 됩니다.

박디자이너: 사용자가 점심만 기록하는 사람일 수도 있으니까 그걸로 충분해요. 푸시 설정에서 일시 중지, 시간 변경, 주간 리포트 알림 끄기를 쉽게 할 수 있어야 해요. 시간대가 바뀌었을 때는 기기 시간에 따라 예약 시간을 다시 계산하고요.

최개발: 푸시 본문에는 음식이나 체중 정보를 넣지 않는 게 좋습니다. 잠금 화면에 “오늘 1,800칼로리 기록했어요”라고 보이면 민감한 내용이 노출될 수 있어요. 일반적인 문구만 보내고, 탭하면 앱 안의 홈이나 리포트로 이동시키겠습니다.

김PM: 푸시 내용에 개인 영양 정보 포함 금지. 리포트 푸시는 주간 리포트가 생성된 다음 사용자 현지 시간으로 주 1회, 사용자가 켠 경우에만 발송. 기록 알림은 하루 최대 한 번, 한 건 이상 기록하면 건너뜀. 일단 이렇게 정리해도 되겠죠?

이대표: 괜찮습니다. 다만 푸시를 안 켜도 리포트는 앱에서 볼 수 있어야 해요.

박디자이너: 당연히요. 리포트 화면에 “지난주 보기”와 날짜 범위 선택이 있어야 하는데, 범위 선택은 너무 복잡하면 안 되니까 이번 주, 지난주 정도만 기본으로 두고 나중에 달력으로 확장할게요.

김PM: 일정으로 넘어가겠습니다. 8주 기준이고, 현재 킥오프 주를 0주차로 볼지 1주차로 볼지 먼저 맞춰야 해요. 제안은 1주차에 요구사항 확정과 디자인 시스템, 기술 검증. 2주차에 상세 설계와 API, DB 골격. 3~5주차 핵심 개발. 6주차 통합과 리포트·푸시. 7주차 QA와 수정. 8주차 스토어 제출 및 출시 준비입니다.

최개발: 8주 안에 양쪽 스토어 실제 승인까지 보장하는 건 어렵습니다. 심사에서 리젝이 나거나 계정 설정 문제가 생기면 며칠에서 일주일이 밀릴 수 있어요. 개발 완료와 스토어 공개일을 구분해야 합니다. 8주차에 후보 빌드와 심사 제출까지를 목표로 잡고, 공개는 승인 일정에 따라 움직이는 게 맞습니다.

이대표: 투자자나 내부 공유에는 8주 후 출시라고 얘기하려고 했는데요. 심사 때문에 확정이 안 되면 어떻게 설명하죠?

김PM: “8주 차 공개 목표, 심사 변수에 따라 1주 버퍼”로 잡으면 됩니다. 내부 일정은 8주차까지 완료를 목표로 하되, 9주차를 완충으로 두는 거예요. 제품 개발을 늦게 시작해서가 아니라 외부 심사라는 변수가 있으니까요.

박디자이너: 디자인 일정은 1주차에 주요 플로우와 와이어프레임, 2주차에 시각 디자인과 상태 화면까지 끝내야 개발이 병렬로 갈 수 있어요. 그런데 음식 검색 결과 UI는 API 필드를 확정해야 정확히 디자인할 수 있습니다. 식품명, 제공량, 칼로리, 브랜드, 출처 라벨이 어느 수준으로 오는지 이번 주 안에 정해야 해요.

최개발: API 업체 샘플 응답은 내일 받아서 필드 비교표를 만들겠습니다. 단위 변환과 데이터 커버리지 확인은 이번 주 금요일까지. 계약 검토가 늦어지면 테스트용 데이터로 화면 개발을 시작하고, 실제 API 연결은 어댑터만 교체할 수 있게 할게요.

김PM: 1주차 요구사항은 이번 회의 내용으로 초안 만들고, 내일 오후까지 코멘트 받겠습니다. 모레 기능 우선순위 확정. 박디자이너님은 금요일에 플로우 초안 공유, 다음 주 화요일까지 주요 화면. 최개발님은 API 검증, 인증 방식, 개인정보 구조 기술 스파이크를 금요일까지 공유하는 걸로요.

이대표: 테스트 사용자 모집은 언제 시작해야 하죠? 출시 직전에 구하면 피드백 반영할 시간이 없을 텐데요.

김PM: 인터뷰는 2주차부터 할 수 있고, 프로토타입은 3주차에 테스트하면 좋겠습니다. 5~6명 정도를 먼저 모집해서 음식 입력 흐름을 보죠. 이후 테스트 빌드는 6주차에 사내 10명, 외부 20~30명 정도로 확대하는 안을 생각하고 있습니다.

박디자이너: 음식 기록은 짧은 사용성 테스트가 중요해요. 참가자에게 “점심에 먹은 밥, 불고기, 반찬을 기록해보세요”라고 부탁하고, 검색 결과에서 어디서 막히는지 봐야 합니다. 테스트 중에 우리가 설명하면 문제가 가려지니까 가능한 한 말을 하지 않고 관찰할게요.

이대표: 테스트 사용자에게 체중이나 식사 사진을 받는 건 조심해야겠네요. 사내 테스트라도 동의가 필요하죠?

최개발: 네. 테스트 목적, 수집 데이터, 보관 기간, 삭제 방법을 안내하고 동의를 받아야 합니다. 테스트 계정 데이터를 실제 분석 시스템에 섞지 않게 별도 태그를 붙이는 게 좋아요. 사진은 테스트 종료 후 삭제 일정을 정하고요. 외부 사용자에게 사례금을 지급하면 연락처와 지급 정보 처리도 분리해야 합니다.

김PM: 테스트 플랜을 두 종류로 나누죠. 첫째 프로토타입 사용성 테스트 5~6명, 실제 개인정보 입력 없이 가상 식단으로 진행. 둘째 베타 빌드 사용성·안정성 테스트 20~30명, 선택 동의 받고 실제 기록을 하되 수집 최소화. 테스트 계정은 일반 서비스 분석에서 제외하거나 별도 표시하겠습니다.

최개발: QA 기준도 지금 정해야 해요. 음식 검색은 한국어 초성이나 띄어쓰기, 브랜드명 일부 검색이 어느 수준까지 돼야 하는지. 데이터가 없는 경우는 직접 입력으로 빠져나갈 수 있어야 하고요. 기록 편집, 삭제, 날짜 변경이 제대로 되는지 테스트 케이스가 필요합니다.

박디자이너: 접근성도 넣어주세요. 칼로리 그래프를 색깔로만 구분하면 색각 이상 사용자는 보기 어렵습니다. 글자 크기를 크게 했을 때 버튼이 잘리지 않는지, 스크린 리더에서 음식 이름과 수량을 읽는지 봐야 해요. 디자인 시스템에 최소 글자 크기와 대비 기준을 명시할게요.

이대표: 너무 세세한 것까지 이번 일정에 다 넣으면 늦어질 것 같은데, 접근성은 어디까지를 MVP에서 합니까?

박디자이너: 색상만으로 상태를 표현하지 않기, 시스템 글자 크기에서 주요 화면이 깨지지 않기, 버튼에 읽을 수 있는 이름 붙이기 정도는 기본이라고 봅니다. 복잡한 차트의 상세 대체 텍스트까지는 기능별로 우선순위를 둘 수 있어요.

최개발: 자동 테스트는 핵심 계산 로직과 API를 중심으로 넣고, 전체 화면을 전부 자동화하는 건 8주 내에 비현실적입니다. 단위 테스트는 양 환산, 날짜 변환, 주간 집계, 누락된 영양소 처리. 통합 테스트는 가입, 식사 생성·편집·삭제, 푸시 토큰 등록, 계정 삭제. UI는 주요 경로 몇 개를 자동화하고 나머지는 수동으로 돌리는 게 좋습니다.

김PM: 구체적으로 테스트 기준을 숫자로 잡을 수 있을까요? 예를 들어 핵심 플로우 성공률이나 크래시율.

최개발: 베타에서 주요 식사 기록 흐름이 95% 이상 완료되고, 치명적인 데이터 유실이 0건이어야 합니다. 크래시 없는 세션 비율은 99% 이상을 목표로 하되, 베타 규모에서는 통계가 충분하지 않을 수 있어요. 검색 API 응답은 대부분 2초 안에 나오는 걸 목표로 하되, 공급자 속도에 따라 캐시와 로딩 화면이 필요합니다.

이대표: 검색이 2초 넘으면 사용자들이 불편해하겠죠. 오래 걸릴 때 먼저 입력한 단어를 보여주고 스켈레톤이 나와야 할 것 같아요.

박디자이너: 로딩 중에도 검색창을 수정할 수 있게 하고, 3초 이상 응답이 없으면 재시도 안내를 보여주는 안으로 디자인할게요. 빈 결과와 오류 결과는 구분하고요. 결과가 없다고 API 장애 메시지를 띄우면 안 됩니다.

김PM: 크래시나 API 오류를 보는 모니터링 도구도 붙여야 해요. 단, 사용자 입력을 수집하지 않는 설정으로. 오류 로그에서 기기 종류, 앱 버전, 요청 ID 정도를 확인할 수 있게 하고요.

최개발: 앱 버전과 플랫폼, 오류 코드, 내부 사용자 식별자 정도는 보낼 수 있습니다. 음식명이나 자유 메모는 자동 첨부되지 않도록 로깅 SDK 설정을 확인하겠습니다. 운영자가 사용자 기록을 직접 조회해야 하는 상황이 생기면 권한 승인과 접근 로그를 남기는 방식으로 하겠습니다.

이대표: 고객 문의가 오면 우리가 해당 사용자 기록을 봐야 문제를 알 수 있지 않나요?

최개발: 필요한 경우에는 사용자 동의를 받고 특정 세션의 진단 정보를 공유하는 기능을 만들 수 있습니다. MVP에서는 관리자 화면을 크게 만들지 말고, 사용자가 문의할 때 직접 기록 ID나 오류 코드를 복사해서 보내게 하는 방식도 있어요. 운영자가 임의로 모든 식사 사진과 내용을 훑어볼 수 있는 구조는 피하는 게 좋습니다.

김PM: 초기 운영 프로세스도 필요하네요. 고객 문의는 이메일이나 앱 내 문의 링크로 받고, 데이터 문제는 사용자 동의 없이 들여다보지 않는 것을 원칙으로 하겠습니다. 관리자 도구가 필요하면 조회 권한을 최소화하고 감사 로그를 남기는 걸로요.

이대표: 화면에 문의 링크가 있어야겠어요. 앱이 오류 나서 문의하는데 앱 안에서 못 찾으면 안 되니까 설정에 넣고, 로그인 실패 화면에도 웹 문의 주소를 보여주세요.

박디자이너: 네. 그리고 음식 정보가 틀렸다고 신고하는 버튼이 있어야 하지 않을까요? 데이터 품질이 낮으면 신뢰가 떨어질 거예요.

최개발: “정보 오류 신고”는 UI와 운영 처리 기준이 필요합니다. MVP에서는 음식 항목 옆에 신고 버튼을 두고, 음식 ID와 신고 유형만 서버로 보내는 건 가능해요. 하지만 접수된 걸 관리하고 수정하는 도구까지 없으면 신고만 쌓입니다. 초기에는 이메일 양식으로 보내되, 음식명과 외부 ID를 미리 채워주는 방식이 현실적입니다.

김PM: 그건 포함합시다. 사용자가 음식 정보 오류를 발견하면 신고 링크로 이동, 자동으로 음식 식별 정보를 넣고, 자유 의견은 선택 입력. 운영에서 주 2회 확인. 다만 영양 정보 수정은 공급자 원본이 있는지 확인한 후 처리해야 합니다.

이대표: 제품에서 직접 숫자를 고칠 수 없는 건가요?

최개발: 우리가 임의로 수정하면 출처와 법적 책임이 생길 수 있어요. 내부 보정이 필요하면 보정값과 근거, 수정자, 시점을 따로 기록하고, 공급자 데이터와 구분해야 합니다. 1차는 명백한 오류를 바로 고치기보다는 공급자에 리포트하고, 사용자에게 해당 항목 데이터를 숨기거나 “정보 확인 중”으로 표시하는 절차가 필요합니다.

박디자이너: 음식 결과 화면에서 출처를 작게 표시할게요. “영양 정보 제공처” 정도요. 사용자가 그 출처를 눌렀을 때 상세 설명을 볼 수 있도록 하면 데이터가 절대값이 아니라는 점도 전달되겠네요.

김PM: 일정상 여기까지 모두 넣으면 빠듯하긴 한데요. 범위 결정을 위해 Must, Should, Could로 한 번 정리하겠습니다. Must는 가입, 선택적 목표 설정, 음식 검색, 직접 음식 추가, 식사 기록 생성·수정·삭제, 기록 목록과 날짜별 조회, 칼로리·탄단지 합계, 기본 주간 리포트, 계정 및 개인정보 설정, 푸시 설정, 계정 삭제. 이 정도에 동의하나요?

최개발: 사진 첨부를 Must에 넣으면 업로드와 권한, 실패 처리까지 같이 들어가요. 전체 범위가 커집니다. 사진이 차별점이라는 판단이면 넣되, 리포트나 검색이 밀리지 않도록 이미지 기능을 뒤쪽 순서로 두고 싶어요.

박디자이너: 사진 기록은 화면에서 아예 언급해놓고 출시 때 빠지는 것보다, 작은 범위로라도 넣는 게 낫다고 봐요. 식사당 사진 한 장, 용량 제한, 수정·삭제 가능. 여러 장 추가나 사진 내 자동 분석은 제외. 이러면 제어 가능하지 않을까요?

최개발: 식사당 한 장이면 괜찮습니다. 다만 사진 업로드 전에 식사 기록을 먼저 저장해야 해서, 사용자 흐름은 “식사 저장 후 사진 추가”가 더 단순해요. 사진 업로드 실패해도 식사 내용은 저장되게 해야 합니다.

김PM: 그러면 Must에 한 장 사진 첨부를 포함하되, 핵심 기록 저장을 막지 않도록 비동기로 처리. 자동 음식 인식은 제외. 검색 API와 기본 기록이 우선이고, 사진은 5주차까지 시간이 남으면 통합하는 순서로 하죠.

이대표: 주간 리포트도 기본이라고 했지만, 어떤 건 이번 버전에 꼭 있어야 하는지 다시 말해 주세요.

박디자이너: 7일 중 기록한 일수, 기록된 날의 평균 칼로리, 탄수화물·단백질·지방 총량 또는 평균, 끼니별 기록 패턴. 지난주 비교는 기록이 충분한 경우에만 보조로. 건강 점수나 “좋음·나쁨” 평가는 제외합니다.

최개발: 영양 정보 누락률도 집계해서 표기해야 합니다. 예를 들어 기록은 15개 음식인데 그중 12개만 칼로리 정보가 있으면 “일부 음식은 합계에 포함되지 않았어요” 안내를 할 수 있어요. 무엇을 분모로 삼을지 정확히 정해야 합니다. 영양값이 하나라도 있으면 포함인지, 칼로리 값이 있을 때만 칼로리 합계에 넣는지요.

김PM: 칼로리 합계는 칼로리 값이 있는 항목만, 단백질은 단백질 값이 있는 항목만 각각 계산하죠. 항목별로 결측값을 따로 처리. 설명 문구는 “일부 음식 정보가 없어 영양소별 합계가 다를 수 있어요” 정도로 통일하겠습니다.

이대표: 목표 달성률은 안 보여주나요?

박디자이너: 목표를 설정한 사용자에게만 보여줄 수 있어요. 그런데 섭취 목표 범위가 개인마다 다르고 추정치라는 점 때문에, “달성”보다는 “설정 목표와 비교”라고 표현해야 해요. 목표를 넘었다고 빨간색 경고를 주는 건 피하고요.

최개발: 목표가 바뀌었을 때 과거 리포트를 현재 목표와 비교할지도 정해야 합니다. 기록 당시 목표를 저장하지 않으면 과거 데이터가 새 목표 기준으로 다시 계산됩니다. MVP에서는 사용자가 목표를 변경하면 이후 날짜부터 적용하고, 목표 변경 이력을 저장하는 편이 일관적입니다.

김PM: 좋은 지적이에요. 목표 테이블에 유효 시작일과 종료일을 두고, 식사 날짜 기준으로 당시 목표를 조회하는 걸로 하겠습니다. 데이터 구조가 조금 복잡해져도 사용자한테는 공정하게 보여야 해요.

최개발: 그럼 목표 변경 기록도 보존해야 하고, 사용자가 계정 삭제하면 같이 삭제합니다. 과거 리포트에 목표가 없었던 날짜는 비교를 안 하고요.

이대표: 개발 인력은 최개발님 혼자 백엔드랑 앱까지 다 하는 건가요? 8주가 맞는지 걱정돼요.

최개발: 앱은 크로스 플랫폼 기반을 쓰고 있어서 화면을 양쪽에 따로 만드는 건 아닙니다. 그래도 백엔드, 외부 API, 푸시, 스토어 빌드, 테스트까지 혼자 전부 깊게 하기는 어렵습니다. API 연결부와 데이터베이스, 인증은 제가 하고, 앱 UI는 다른 개발자 지원이 0.5명이라도 있으면 일정이 안정됩니다.

김PM: 인력 계획은 다시 확인하겠습니다. 프론트 지원을 몇 주차부터 몇 주 동안 받을 수 있는지 오늘 안에 조율할게요. 박디자이너님 디자인 시스템 산출물을 개발에 빨리 전달해주시면 최개발님이 화면 뼈대를 먼저 잡는 식으로 병렬화하겠습니다.

박디자이너: 화면마다 완성도를 기다리기보다 버튼, 입력창, 카드, 빈 상태처럼 공통 컴포넌트를 먼저 전달할게요. 2주차 중반부터 개발 가능한 상태로 순차 전달하겠습니다. 대신 요구사항이 자주 바뀌면 시안 수정이 반복되니까 이번 주 우선순위는 확정해야 해요.

이대표: 저는 아직 자동 사진 분석을 완전히 포기한 건 아니에요. 경쟁 앱을 보면 그게 기사 제목으로 나오니까요. 최소한 기술 가능성은 검증해봅시다.

최개발: 검증 자체는 할 수 있어요. 공개된 사진 샘플이나 우리가 만든 음식 사진 100장 정도로 한국 음식 분류 정확도와 응답 비용을 보죠. 다만 한식 혼합 메뉴는 단일 라벨만으로 부족하니까, 음식 항목 여러 개를 추출하는 수준을 따로 확인해야 해요. 결과가 그럴듯해도 양 추정 정확도는 또 다른 지표고요.

김PM: 그럼 기술 검증을 1주차에 제한된 스파이크로 하되, 핵심 개발 일정과 분리합시다. 성공 기준을 정해야 하는데요. 사진에서 음식 종류를 대략 맞히는 정확도가 80% 이상이면 MVP에 넣는다는 식으로 할까요?

최개발: 정확도만으로는 부족해요. 음식명을 맞혔어도 칼로리나 양이 틀리면 기록으로 쓰기 어렵습니다. 우선 식사 내 음식 항목 분리 정확도, 라벨 정확도, 사용자 수정 비율, 응답 시간, 요청 비용을 같이 보겠습니다. 100장으로는 통계적 확신이 낮다는 점도 보고서에 명시하고요.

박디자이너: 사진 결과를 사용자가 확인하고 수정하는 화면까지 만들어야 의미가 있어요. 예를 들어 자동으로 두 가지 음식을 제안하고, 사용자가 “이거 아닌데요”로 지우거나 양을 편집하는 방식. 자동 결과를 바로 저장하면 안 됩니다.

이대표: 네, 그 화면이 들어가야 하는 건 이해했어요. 그런데 사진을 저장만 하면 사람들이 잘 안 쓸 수도 있겠네요.

박디자이너: 그래서 베타 사용자 인터뷰에서 사진을 어떤 상황에 쓰는지 확인하면 돼요. 메뉴 이름을 검색하기 어려운 식당, 양을 나중에 기억하고 싶은 경우, 하루 기록을 시각적으로 모아보는 경우가 다를 수 있어요. 자동 인식이 아니어도 가치가 있는지 먼저 봅시다.

김PM: 사진 분석은 1주차 기술 검증 결과로 재논의. 8주 MVP의 기본 약속에는 포함하지 않음. 대신 사진 첨부는 포함. 그렇게 해도 괜찮겠죠?

이대표: 네, 다만 검증 결과가 좋으면 넣을 수 있는 여지는 열어두죠. 그럼 요금은 출시 후 언제 다시 논의하나요?

김PM: 베타에서 4주 정도의 실제 사용 데이터를 보고, D7 유지율, 주간 기록 일수, 검색 실패율, 리포트 열람률을 검토한 뒤 2차 로드맵과 과금 실험을 제안하겠습니다. 출시 전에 가격 화면을 테스트하는 건 별도 사용자 조사로 가능하지만, 결제 기능은 이번에는 넣지 않습니다.

최개발: 분석 이벤트 설계는 지금 해야 나중에 비교가 됩니다. 가입 완료, 목표 설정 여부, 첫 기록 완료, 두 번째 날 기록, 검색 결과 선택, 직접 입력, 사진 첨부, 리포트 열람, 푸시 허용 여부 정도를 익명 이벤트로 기록할 수 있어요. 음식 내용이나 목표 몸무게는 보내지 않고요.

이대표: 유지율은 계정 정보를 써야 계산할 수 있죠? 완전히 익명이면 어떤 사용자가 다시 왔는지 모를 텐데요.

최개발: 서비스 내부 사용자 ID를 랜덤으로 만들어서 앱 분석 ID와 연결하면 됩니다. 이름, 이메일은 분석 도구로 보내지 않아요. 광고 식별자를 쓰는 것도 이번에는 피하는 게 좋습니다. 개인정보 처리방침에 분석 도구 사용을 명시하고, 필요하면 옵트아웃 설정을 제공해야 합니다.

박디자이너: 설정에 분석 데이터 전송 끄기를 넣으면 좋겠지만, 화면과 개인정보 설계가 하나 더 늘겠네요. 필수 서비스 로그와 선택적 제품 분석은 분리해서 생각해야 해요. 사용자가 분석을 거부해도 식사 기록 앱 기능은 정상적으로 돌아가야 하고요.

김PM: 선택적 제품 분석은 거부할 수 있게 하되, 서비스 보안과 장애 대응을 위한 최소 로그는 별도로 안내하는 방향으로 개인정보 담당과 확인하겠습니다. 이벤트 이름과 속성 목록은 최개발님이 초안 작성하고 제가 동의 문구를 검토할게요.

최개발: 푸시 동의도 별도로 필요합니다. 운영체제 권한만으로 충분한지, 앱 내에서 알림 종류별 동의를 한 번 더 받을지 확인해야 해요. 저는 앱 설정에서 기록 알림과 주간 리포트 알림을 각각 켜고 끌 수 있게 하고, 최초 권한 요청 전에 설명 화면을 한 번 두는 걸 추천합니다.

이대표: 알림을 한 번 거부하면 다시 요청할 수 없나요?

최개발: 운영체제에서 알림 권한을 거부하면 앱이 팝업을 반복해서 띄우기 어렵습니다. 설정 앱으로 이동하는 링크를 보여줄 수는 있어요. 그래서 첫 실행 즉시 권한 팝업을 띄우면 거부율이 높을 수 있고, 사용자가 알림의 가치를 알았을 때 요청해야 합니다.

박디자이너: 첫 기록을 저장한 직후에 “기록 시간을 놓치지 않도록 알림을 설정할까요?”라고 제안하고, 나중에 하기를 둘게요. 권한을 허용하지 않아도 앱을 계속 쓸 수 있게 하고요.

김PM: 좋습니다. 다만 첫 기록 완료 직후에 또 팝업이 뜨면 흐름이 끊길 수도 있어요. 완료 화면에서 인라인 카드로 제안하고, 탭했을 때 운영체제 권한 요청을 띄우는 건 어떨까요?

박디자이너: 네, 인라인 카드면 강제성이 덜하네요. “지금 설정”과 “괜찮아요”를 선택하게 하겠습니다. 설정 화면에서도 언제든 켤 수 있게 하고요.

최개발: 알림 예약을 수정할 때 서버 푸시 작업이 이전 설정을 취소해야 합니다. 시간대를 바꾸거나 알림을 끄면 이미 큐에 들어간 작업도 취소하거나 발송 시점에 설정을 재확인해야 해요. 발송 직전에 사용자의 최신 설정과 해당 날짜 기록 여부를 확인하는 구조로 하겠습니다.

이대표: 개인 정보 쪽에서 데이터 보관 기간을 얼마나 잡을까요? 탈퇴 안 한 사용자의 식사 기록은 계속 보관해도 되는 건가요?

김PM: 서비스 제공에 필요한 기간 동안 보관하되, 장기 미사용 계정은 별도 정책을 마련해야 합니다. 지금 1차 출시에서 휴면 계정 분리까지 구현할지, 정책만 두고 알림을 나중에 할지 검토하겠습니다. 법무 자문이 필요한 내용이라 제가 초안으로 단정하지 않을게요.

최개발: 기술적으로는 마지막 로그인과 마지막 기록 시점을 보관하면 미사용 계정을 찾을 수 있습니다. 다만 자동 삭제는 사용자 데이터 손실로 이어질 수 있으니, 사전 안내와 유예기간이 있어야 합니다. MVP에서는 탈퇴 요청 시 삭제 흐름을 우선 구현하고 장기 미사용 자동 삭제는 정책 확정 전까지 넣지 않는 게 안전합니다.

박디자이너: 개인정보 화면에서 사용자가 저장된 항목을 확인할 수는 없나요? 목표 정보, 알림 설정, 사진이 있는 기록을 각각 보여주는 정도요.

이대표: 계정 삭제만 있으면 충분하지 않을까요? 데이터 다운로드도 아직 안 넣는다고 했고요.

김PM: 개인정보 열람권 대응을 위해 앱 안에서 최소한 프로필 정보와 기록 목록에 접근할 수 있어야 합니다. 기록 자체는 날짜별 조회로 보이지만, 서버에 어떤 정보가 있는지 한눈에 보여주는 기능은 별도예요. 다운로드가 필수인지, 요청 시 처리로 충분한지 법무 확인이 필요합니다. 8주 MVP에서는 설정과 계정 삭제를 우선하고, 데이터 사본 다운로드는 요구사항 확인 후 결정하겠습니다.

최개발: 다운로드 기능은 CSV 정도로 제한하면 구현은 아주 크진 않지만, 사진 포함 여부, 영양 정보 설명, 기간 선택, 비동기 생성 같은 걸 정해야 합니다. MVP 막바지에 추가하면 QA가 부족해질 수 있으니 2주차 전에 결정해야 합니다.

박디자이너: 목표 입력 화면의 문구도 한번 정해보죠. “감량 목표를 설정하세요”라고 하면 다이어트 앱 느낌이 강해요. “어떤 방식으로 기록을 시작할까요?” 아래에 “식사 습관 확인”, “체중 목표 설정”, “목표 없이 기록” 세 옵션을 두면 어떨까요.

이대표: 저는 목표가 있어야 계속 쓸 것 같은데, 세 선택지를 똑같이 두면 대부분 목표 없이 시작해서 리포트가 단순해질 수 있지 않을까요?

최개발: 목표 계산 로직은 실제로 데이터가 충분히 입력된 경우에만 돌아가게 하고, 입력이 덜 됐으면 임의 숫자를 만들지 않겠습니다. 칼로리 목표를 자동 제안할 때 사용자가 목표를 다시 조정할 수 있어야 하고, 상한·하한 정책도 필요해요. 너무 낮은 숫자를 입력하면 경고를 띄우거나 저장을 막을지 정해야 합니다.

이대표: 위험한 목표를 저장하는 걸 막아야 하지 않나요? 사용자가 하루 500칼로리로 설정하면 앱이 그걸 따라가면 안 될 것 같은데요.

박디자이너: 동의해요. 다만 너무 구체적인 의학적 판단을 우리가 하는 것도 부담입니다. 입력값이 특정 기준보다 낮으면 “건강에 적절하지 않을 수 있어 설정할 수 없습니다. 전문가와 상담하세요”라고 막을 수는 있겠지만, 그 기준을 전문가가 검토해야 합니다.

김PM: 이번 버전에서 사용자가 칼로리 목표를 직접 입력하는 기능은 넣지 않고, 제공된 선택지 안에서 목표를 고르게 할까요? 최개발님, 계산 기준과 안전 범위까지 8주 내 검토 가능합니까?

최개발: 계산 자체는 가능해도 제품과 법률 기준이 필요한 부분이라 제가 숫자를 임의로 정하면 안 됩니다. 기본 권장 목표를 넣을지, 사용자가 목표 없이 기록하고 프로필 기반으로 참고치를 계산할지 전문가 검토를 받아야 합니다. 일단 온보딩에서는 목표 유형만 받되, 칼로리 숫자는 전문가 자문 결과가 있을 때만 표시하는 게 안전합니다.

이대표: 그러면 목표 기능이 너무 약해지잖아요.

김PM: 전문가 검토를 일정에 넣겠습니다. 이번 주 안에 질문 목록을 보내고, 다음 주 초 의견을 받는 걸 목표로 하죠. 결과가 늦으면 MVP에서 자동 칼로리 목표는 제외하고, 사용자가 기록한 영양 정보와 주간 패턴만 제공합니다. 릴리스 범위를 지키기 위해 그 결정을 미리 정해두는 거예요.

박디자이너: 화면 설계는 목표 설정을 끌 수 있게 만들어두되, 목표 수치가 없을 때도 자연스럽게 보이게 하겠습니다. 칼로리 숫자가 빠져도 “기록된 식사”와 “이번 주 패턴”은 그대로 제공할 수 있어요.

이대표: 알겠습니다. 목표 수치가 핵심이라고 생각했는데, 검토 없이 숫자를 보여주는 게 더 위험하다는 건 이해했어요.

김PM: 그럼 오늘 논의한 우선순위를 다시 읽겠습니다. MVP는 모바일 iOS·안드로이드 공통 앱. 이메일·애플·구글 인증을 우선 검토하고 카카오 로그인은 2차. 가입 후 목표 없이도 시작 가능. 음식 검색, 최근 기록 복사, 직접 음식 입력, 끼니 기록, 양 조절, 편집·삭제, 사진 한 장 첨부. 사진 자동 인식은 기술 검증만 하고 출시 필수에서 제외. 기본 영양소는 칼로리, 탄수화물, 단백질, 지방이고, 데이터가 없는 값은 0으로 오인시키지 않습니다.

최개발: 데이터는 사용자와 프로필, 목표 이력, 음식 마스터, 식사, 식사 음식 항목, 알림 설정, 동의 이력 중심. 음식 영양값은 기록 시점 스냅샷으로 저장. 식사 사진은 별도 스토리지에 저장하고 DB에는 키만. 외부 음식 API 응답은 내부 표준 모델로 바꾸고, 사용자 정보는 공급자에 보내지 않습니다. 검색 실패 시 최근 기록이나 직접 입력으로 계속 기록할 수 있게 합니다.
